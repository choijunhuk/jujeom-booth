# Booth server API contract

Single Node process: HTTP API + SSE + static files. Zero dependencies. This is the source of truth for frontend code. Config files (`menu.json`, `rewards.json`, `tables.json`) are read once at boot.

## 1. Base path, pages, static files

`BASE` = env `BASE_PATH` (default `""`, production `/booth`). nginx forwards the full path unchanged, so every route below lives under `BASE`.

**The frontend learns the base path from the server.** In every served `.html`, `.js` and `.css` file the literal token `__BASE__` is replaced with `BASE` (`""` or `/booth`, never a trailing slash). Write:

```html
<script src="__BASE__/static/base.js"></script>   <!-- public/base.js is exactly: window.BASE = "__BASE__"; -->
<script src="__BASE__/static/guest.js"></script>
<link rel="stylesheet" href="__BASE__/static/guest.css">
```

and call the API as `fetch(window.BASE + '/api/...')`. Never hard-code `/booth` or an absolute `/api`. Use relative-to-BASE URLs for `EventSource` too.

| Route (prefix with BASE) | Served file in `public/` | Notes |
|---|---|---|
| `/` (and `BASE` without slash) | built-in landing text | "scan the table QR" |
| `/t/<token>` | `guest.html` | 404 page for unknown token. Sets the `booth_d` device cookie. The token is the last path segment: `location.pathname.split('/').pop()` |
| `/wait` | `wait.html` | sets `booth_d` cookie |
| `/staff` | `staff.html` | page is public; it must show a PIN form and call login |
| `/staff/qr` | `qr.html` | page is public; data comes from `GET /api/staff/tables` (needs login) |
| `/kitchen` | `kitchen.html` | page is public; data needs the staff session |
| `/board` | `board.html` | public |
| `/sw.js` | `public/sw.js` | the booth service worker, **exactly** at `BASE/sw.js` (GET/HEAD). `Content-Type: text/javascript`, `Cache-Control: no-cache`, `Service-Worker-Allowed: <BASE>/` (so its scope is `BASE/`; `/` when BASE is empty), `__BASE__` substituted. 404 if the file is missing. Register it with `navigator.serviceWorker.register(window.BASE + '/sw.js', { scope: window.BASE + '/' })`. |
| `/static/<path>` | `public/<path>` | any file under `public/` (also `guest.html` etc.). Allowed extensions: html js mjs css json svg png jpg jpeg gif webp ico woff woff2 txt mp3 ogg wav webmanifest. Dotfiles and `..` -> 404. `Cache-Control: public, max-age=60` (HTML pages: `no-cache`). Put games at e.g. `public/games/pour.js` -> `__BASE__/static/games/pour.js` |

If a page file is missing the server answers a 404 page.

Security headers on everything: `X-Content-Type-Options: nosniff`, `Referrer-Policy: same-origin`, `X-Frame-Options: DENY`, CSP `default-src 'self'; script-src 'self'; worker-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data: blob:; media-src 'self' data: blob:; font-src 'self' data:; connect-src 'self'; object-src 'none'; base-uri 'self'; frame-ancestors 'none'; form-action 'self'`. So: **no inline `<script>` and no inline event handlers (`onclick=` etc.) — scripts must be separate `.js` files from `__BASE__/static/`** (put `window.BASE` in `public/base.js`, loaded first). Inline `<style>`/`style=` is still allowed. No external scripts/fonts/CDNs; images may be `data:`/`blob:`.

## 2. Conventions

- All API paths are `BASE/api/...`. All bodies/responses are JSON UTF-8. Times are epoch milliseconds. Money is integer won.
- **Every POST must send `Content-Type: application/json`** (even with body `{}`), otherwise 415. Body limit 16 KB (413). **One exception:** the photo upload `POST /api/staff/menu/items/<id>/photo` takes the raw image bytes (`image/jpeg|png|webp`, max 400 KB), see Menu photos.
- Error response (any non-2xx): `{ "error": "<code>", "message": "<Korean text safe to show>", ...extra }`. Switch on `error`, not on `message`.
- Common errors: 400 `bad_json`, 401 `unauthorized`, 403 `bad_origin`, 404 `not_found`/`no_table`, 413 `too_large`, 415 `unsupported_media_type`, 429 rate/limit codes, 500 `internal`, 503 `busy`.
- `table` is always the table number (1..N). Table numbers are also their ids.
- Cookies (both `HttpOnly`, `SameSite=Lax`, `Path=BASE||"/"`, `Secure` when `COOKIE_SECURE=1`): `booth_d` = anonymous device id, server-signed (`<id>.<signature>`; opaque to pages — never parse or forge it; an old or invalid value is silently replaced by a new one, so after an upgrade a browser just becomes a "new" device) (set automatically on guest pages/APIs, 3 days; used for nicknames, play limits, wait list), `booth_s` = staff session (default 72 h, env `SESSION_HOURS`), `booth_k` = staff trusted-device key (30 days, set on a successful login; see login). Names are prefixed so they cannot collide with the main site's cookies; if the browser sends duplicates of a name (different Paths), the server accepts any valid `booth_s` and the first well-formed `booth_d`. `fetch` on the same origin sends them automatically; no `credentials` option needed.
- Staff POSTs are rejected with 403 `bad_origin` when `Sec-Fetch-Site` is present and not `same-origin`/`none`, or (if that header is absent) when `Origin` is present and differs from `PUBLIC_ORIGIN`/`Host`. Normal same-origin `fetch` is fine.

## 3. Shared object shapes

**Menu item**: `{ id, name, price, cat, desc, soldOut, photo, stockLeft }` — **`stockLeft` (H10)**: for guests `null` unless a count is set AND it is 5 or less (show "N개 남음"); staff see the exact number (`null` = unlimited). `photo` is `null` or a path **relative to BASE** such as `/photos/12-ab12cd34.jpg` (use `<img src="` + `window.BASE` + `item.photo + `">`; the file name changes on every replace, so it can be cached forever). **Menu** (guest view): `{ categories: string[], items: MenuItem[] }` — items and categories come in the menu's display order; **hidden items never appear**, and a category with no visible item is omitted. The menu lives in the database and staff can edit it at any time (section 6, "Menu management"): re-render from every new `state`/`GET`, never cache prices for long. `price` is a multiple of 100 won. New item ids look like `m` + 10 hex chars; items seeded from `menu.json` keep their ids.
**Staff menu view** (inside staff `state` and in every menu-management response, as `menu`): same shape but includes hidden items, each item additionally has `hidden: boolean`, `sortOrder: number`, `categoryId: number`, `inUse: boolean` (it appears in some order, so it cannot be deleted), `stockAuto: boolean` (true while `soldOut` was set automatically by the stock counter reaching 0), and `stockLeft` is exact, and `categoryList: [ { id, name, sortOrder, itemCount } ]` lists every category including empty ones.

**Order**
```json
{ "id": 12, "table": 3, "seat": 1, "status": "pending|cooking|served|cancelled", "paid": false,
  "items": [ { "id": "tteokbokki", "name": "떡볶이", "qty": 2, "unitPrice": 8000, "service": false } ],
  "subtotal": 16000, "memberDiscount": 1600, "couponDiscount": 1000, "discount": 2600, "total": 13400,
  "member": true, "couponCode": "K3F9X2",
  "depositor": "홍길동", "paidBy": "auto",
  "createdBy": "guest|staff", "memberRule": null,
  "paidAmount": 13400, "paidMethod": "transfer|cash|other|null", "paidAt": 1731480000000,
  "balanceDue": 0, "overpaid": 0, "refundedAmount": 0, "refundDue": 0, "writtenOff": false,
  "note": "", "createdAt": 1731480000000, "updatedAt": 1731480000000, "cookingAt": null }
```
`depositor` is the name the guest typed for the bank transfer (`null` if none); `paidBy` is `null` (unpaid), `"staff"` (a staff member marked it, or assigned a deposit notice) or `"auto"` (confirmed automatically from a bank deposit notice). `couponCode` is `null` when none. `total = subtotal - memberDiscount - couponDiscount` (never below 0); `discount = memberDiscount + couponDiscount` is kept for older code. `member` is true when the order was placed by a verified COMS club member (the club id is never exposed). Amounts and item names/prices are frozen when the order is created: later menu edits, renames or price changes never alter an existing order (staff line edits, H2, keep them too for lines already on the order). Status flow: `pending` (waiting for staff accept) -> `cooking` -> `served`; `cancelled` is terminal.
**New in Release 2 (all derived from the money actually received):**
- `items[].service` (H3): a free "service" line (`unitPrice` 0, never part of `subtotal`).
- `createdBy` (H1): `"staff"` for orders made with `POST /api/staff/tables/<n>/orders`, otherwise `"guest"`. `memberRule`: the member-discount rule that was applied when the order was created (`{ mode, pct, amount, maxDiscount, minOrder }`) or `null` if no member discount applies (orders from before this field existed get a fixed rule equal to the discount they received, `legacy: 1`, so editing them keeps it); staff edits re-apply this stored rule, never today's settings.
- `paidAmount` (H5): money received for this order so far (partial payments add up); `paidMethod`: method of the latest payment; `paidAt`: when the order became fully paid (`null` while unpaid). **`paid` is true exactly when the money held (`paidAmount` minus refunds already paid back) covers `total`** (and the order is not free-and-unpaid). `balanceDue` = what is still missing (0 when `paid` or cancelled). `overpaid` = money held above `total` (0 for cancelled).
- `refundDue` / `refundedAmount` (H6): money that must still be handed back / was already handed back. A cancelled order owes everything it received; a live order owes `paidAmount - total` when overpaid or after an edit lowered the total. `writtenOff` (H7): the order was left unpaid when staff force-cleared its table (미수금).
- `updatedAt` strictly increases on every change of the order (H15), so it can be sent back as `expectedUpdatedAt`.

**Coupon**
```json
{ "code": "K3F9X2", "rewardId": "d1000", "source": "score|hour|staff", "type": "discount|item",
  "amount": 1000, "item": null, "label": "안주 1,000원 할인", "status": "issued|used|void",
  "table": 3, "seat": 1, "orderId": null, "usedAt": null, "createdAt": 1731480000000 }
```
`amount` is set for `discount`, `item` (string) for `item` coupons. `source: "staff"` = made by hand (H11); `status: "void"` = cancelled by staff: it can no longer be applied or redeemed and is not shown to guests. Code alphabet has no `I O 0 1`; codes are upper-case, matching is case-insensitive.

**Game config** (`games` map in guest snapshot / `gameInfo` on board): `{ "pour": { "label", "maxScore", "minDurationMs" }, "cheers": {...} }`. Valid game ids are the keys of `games` in `rewards.json` (currently `pour`, `cheers`, `bug`, `typing`); nothing in the server assumes a fixed set, boards and rankings sum whatever games exist. `public/landing.html`, when present, replaces the built-in landing page at `BASE/` (`__BASE__` substituted, normal HTML headers); the built-in page is titled COMHERE.

## 4. Guest API (`BASE/api/t/<token>/...`)

Unknown token -> 404 `no_table`. Tokens are 16 chars of `[A-Za-z0-9_-]`. A guest only ever sees the table's **current seat** (round); staff "clear table" increments the seat, so old orders/coupons/calls disappear.

### `GET /api/t/<token>` — full snapshot (also the polling fallback; poll every ~5 s)
```json
{ "table": { "number": 3, "seat": 1 },
  "orderingOpen": true,
  "memberDiscountPct": 10,                   // older field = memberDiscount.pct
  "memberDiscount": { "enabled": true, "mode": "percent", "pct": 10, "amount": 1000, "minOrder": 0, "maxDiscount": 0, "stackWithCoupon": true },   // the staff-defined rule (display only); `enabled` = staff switch AND the feature is configured on the server. See GET .../member for whether THIS visitor is a member
  "menu": { "categories": [...], "items": [ MenuItem ] },   // hidden items are never included
  "orders": [ Order ],                       // current seat, newest first; cancelled orders: only the newest 5 are included
  "coupons": [ Coupon ],                     // current seat, oldest first
  "calls": [ { "id": 5, "type": "물", "createdAt": 0 } ],   // open staff calls
  "nick": "맥주왕",                          // this device's nickname for this seat, or null
  "rewards": [ { "id": "d1000", "game": "cheers", "label": "...", "type": "discount", "amount": 1000, "item": null,   // ACTIVE rewards only (staff can edit them any time; re-render on every state)
                 "threshold": 700, "soldOut": false, "got": false } ],
  "games": { "pour": { "label": "...", "maxScore": 500, "minDurationMs": 8000 }, "cheers": {...} },
  "notice": { "text": "주문이 밀려요", "level": "info|warn" } | null,   // H9: staff banner
  "callTypes": ["물", "수저", "치워주세요", "기타"],
  "pay": { "bank": "", "account": "", "holder": "", "tossEnabled": false, "kakaoPayUrl": "", "requireDepositor": false } }   // staff-editable payment settings (first boot: env PAY_BANK/PAY_ACCOUNT/PAY_HOLDER); empty strings if unset
```
`pay` is for the payment screen: show the account with a copy button. If `tossEnabled`, the page builds the Toss link itself from bank / account / the order total (the server generates no deep links); if `kakaoPayUrl` is not empty it is a staff-checked `https://qr.kakaopay.com/...` link to offer as a "카카오페이로 보내기" button. If `requireDepositor`, the order form must ask for the depositor name (the order is refused with 400 `depositor_required` otherwise).

### `POST /api/t/<token>/orders`
Body `{ "key": "<8-64 chars [A-Za-z0-9_-]>", "items": [ { "id": "tteokbokki", "qty": 2 } ], "couponCode": "K3F9X2"?, "note": "덜 맵게"?, "depositor": "홍길동"?, "expectedTotal": 15000? }`.
**New — `expectedTotal`** (optional integer, the total the guest saw on screen, after discounts): if it differs from the total the server computes now, the server answers **409 `price_changed`** and creates nothing. Payload: `{ error, message, expectedTotal, total, subtotal, memberDiscount, couponDiscount, items: [ { id, name, qty, unitPrice } ] }` with the fresh values. The page shows them, asks the guest to confirm, then resends with `expectedTotal` = the fresh `total`. **Nothing was created, so the client may reuse the same `key` or send a new one — both work.** Without `expectedTotal` the current price is charged as before. A non-integer value -> 400 `bad_expected_total`. Replays of an already-created key (`duplicate: true`) are answered before this check.
Generate `key` once per cart submission (`crypto.randomUUID()`), reuse it on retries. Prices sent by the client are ignored.
**New — `depositor`** (optional string; the name on the bank transfer): control/invisible characters are stripped, whitespace collapsed, 1..10 visible characters (no profanity filter); an empty string counts as absent. When staff turned on `requireDepositor` it is mandatory: 400 `depositor_required`. Invalid -> 400 `bad_depositor`. It is stored on the order and a replay of the same `key` returns the stored order unchanged. Staff use it (together with the amount) to match bank deposit notices.
- 201 `{ "order": Order, "duplicate": false, "memberDiscountSkipped": "limit"?, "couponIgnored": true? }` — **`couponIgnored: true`** (new) appears when the sent `couponCode` is valid but would discount 0 won (e.g. a free item, or nothing left after the member discount): the order is created without it, `order.couponCode` is `null` and the coupon stays unused. Tell the guest the coupon was not applied and is still available. — `memberDiscountSkipped: "limit"` appears only when the guest is a member who would have got a discount but already used it on the maximum number of orders (default 20 per club member, env `MEMBER_ORDER_MAX`); the order was created at full price. Show a short notice.
- 200 `{ "order": Order, "duplicate": true }` when this table **in its current seat** already used that key (the key is scoped to table+seat: after staff clears the table the same key creates a new order; returns the original; checked before everything else, even when ordering is closed).
- 400 `bad_key`, `bad_items` (empty / malformed), `too_many_lines` (>30 lines), `bad_qty` (not integer 1..20; `id` in payload), `dup_item` (same id twice), `unknown_item` (`ids`; also returned for hidden items), `bad_note` (>100 chars), `bad_coupon` (not found / not this table+seat), `coupon_not_discount`
- 409 `closed` (ordering switched off), `sold_out` (`ids`, `names`), `coupon_used`, `coupon_void` (H11), **`insufficient_stock`** (H10: `{ id, left, ids, names, items: [ { id, name, left } ] }` — the first short item and all of them; nothing was created, show "N개만 남았어요")
- 429 `too_many_pending` (10 orders waiting for acceptance at once)
- 429 `too_many_orders` (**new**: at most 40 orders per table per seat, cancelled ones included; resets when staff clears the table). Message tells the guest to ask staff.

A discount coupon is marked used together with the order; it returns to `issued` if the order is cancelled.

**Member discount.** Membership is decided by the server only: it forwards the visitor's club-site login cookie to the club backend (feature off unless env `COMS_ME_URL` is set). The request body is never trusted for membership (fields like `member` are ignored). The rule is set by staff (`POST /api/staff/member-discount`, below): `enabled`, `mode` (`percent` | `fixed`), `pct`, `amount`, `minOrder`, `maxDiscount`, `includeAssociate`, `perMemberLimit`, `stackWithCoupon`. For an eligible member the order's `memberDiscount` is computed as: 0 if `subtotal < minOrder`; otherwise percent mode `floor(subtotal * pct / 100 / 100) * 100` (rounded DOWN to 100 won; 8,500 won at 10% = 800, at 15% = 1,200; 900 won at 10% = 0) or fixed mode `amount`; then `min(discount, maxDiscount if maxDiscount > 0, subtotal)`. It is applied to the subtotal **first**; a selected coupon is then applied to what is left; the total never goes below 0. Eligible = verified club member AND staff switch `enabled` AND (`includeAssociate` OR the club role is not `ASSOCIATE`). When `stackWithCoupon` is false and the guest selected a coupon, the coupon wins: the member discount is 0 and the 201 response carries `memberDiscountSkipped: "coupon"`. When the member already used the discount on `perMemberLimit` non-cancelled orders the order is created at full member-less price with `memberDiscountSkipped: "limit"` (the limit is only known at order time). Cancelling an order restores its coupon and frees its member-discount slot. `expectedTotal` / 409 `price_changed` protects the guest against any mismatch between the shown and the computed total.

### `GET /api/t/<token>/member`
-> `{ "enabled": boolean, "member": boolean, "mode": "percent"|"fixed", "pct": number, "amount": number, "minOrder": number, "maxDiscount": number, "stackWithCoupon": boolean }`. `enabled` is false when the feature is off — either not configured on the server or switched off by staff (no outbound request is made then). `member` is true when the browser's club login is valid right now (cached 60 s) AND the visitor is eligible under the staff rule (the `ASSOCIATE` role is excluded when staff set `includeAssociate: false`; the per-member limit is NOT considered here, it is reported at order time via `memberDiscountSkipped`). The other fields are the rule, so the page can display and pre-compute the discount (subtotal >= `minOrder`; percent: `floor(subtotal*pct/10000)*100`, fixed: `amount`; then cap by `maxDiscount` when > 0 and by the subtotal; if `stackWithCoupon` is false a selected coupon replaces it). Only these fields are returned: never a name, id or role. The actual discount is always decided again at order time. Cheap to call; do not poll faster than every ~30 s. Not logged in / expired / banned / club server down all simply give `member: false`.
**Rules the page must know (new):** (1) a lookup needs a `booth_d` device cookie that already existed when the request arrived — the first request of a brand-new browser (which only mints the cookie) answers `member: false`; load the guest snapshot first (every guest page does), then call `/member`, and call it again once the first answer was `false` while a club login cookie is present only if you want a retry. The same applies to the member discount at order time. (2) Each device gets at most 6 uncached lookups per minute; beyond that it is simply treated as a non-member until the minute passes. (3) Only definitive answers are cached for 60 s: a valid member, or the club saying 401/403. Timeouts, 5xx, 429, redirects and unreadable answers are never cached (the next call asks again). (4) Any logged-in club account counts as a member; the `ASSOCIATE` role only if staff left `includeAssociate` on (default on). (5) A guest who logs out of the club site keeps the discount for up to 60 s (cache).

### `POST /api/t/<token>/orders/<orderId>/cancel` — body `{}`
Only own-table, current-seat, `pending` orders with NO money received (a partly paid order is refused too). 200 `{ order }`. 404 `no_order`, 409 `not_cancellable`.

### `POST /api/t/<token>/orders/<orderId>/depositor` — body `{ "depositor": "홍길동" }`
Lets the guest fix the depositor name of an own, current-seat order while it is unpaid. 200 `{ order }`. 400 `bad_depositor`, 404 `no_order` (also another table's order), 409 `already_paid`, 409 `order_cancelled`. (A deposit notice that already arrived with the old name stays pending for staff; it is not re-matched automatically.)

### `POST /api/t/<token>/nick` — body `{ "nick": "맥주왕" }`
Control, zero-width, bidi, Hangul-filler (U+3164, U+115F, U+1160, U+FFA0), braille-blank and lone-surrogate characters are stripped, whitespace collapsed; at least one visible character (checked after NFKC) and 1..10 characters are required; profanity blocklist. The stored nick keeps the typed form. 200 `{ "nick": "<cleaned>" }`. 400 `bad_nick`. Per device per seat. Shown on the board. **New errors:** 400 `no_device` (the request did not carry an existing valid `booth_d` cookie — a cookie minted by this very response does not count; load `GET /api/t/<token>` first, which every guest page does; after a `no_device` just retry), 429 `too_many_nicks` (30 nicknames per table seat; existing devices can still rename).

### `POST /api/t/<token>/plays/start` — body `{ "game": "pour" }`
200 `{ "playId": 41, "game": "pour", "startedAt": 0, "maxScore": 500 }`. Server records the start time. 400 `bad_game`; 429 `rate_limited` (`retryAfterMs`; max 1 start per 3 s per device **and, new, 1 start per 1 s per table seat** — friends at the same table starting together may need to retry after `retryAfterMs`), `device_limit` (200 plays per device total), `seat_limit` (**new**: 300 plays per table seat in total), `too_many_open` (**new**: 20 started-but-unfinished plays (younger than 10 min) per seat).

### `POST /api/t/<token>/plays/finish` — body `{ "playId": 41, "score": 430 }`
`score` must be an integer. Accepted once per play.
200:
```json
{ "score": 430,
  "coupons": [ Coupon ],                       // newly issued by this finish
  "rewards": [ { "rewardId": "drink", "label": "음료 1잔",
                 "result": "issued|low_score|already_got|sold_out", "coupon": Coupon /* only when issued */ } ] }
```
`rewards` lists every reward of this game so the UI can say "재고 소진" / "점수 부족" / "이미 받음".
Errors: 400 `bad_play`, 400 `bad_score` (non-integer, or outside `0..maxScore`), 400 `too_fast` (shorter than the game's `minDurationMs`), 400 `too_slow` (>10 min), 404 `no_play` (unknown play / other device / other table / seat was cleared or the table was moved away), 409 `already_finished`. A play rejected for `bad_score` (range) / `too_fast` / `too_slow` is burned: it cannot be resubmitted (further finish -> 409). Malformed values (`bad_play`, non-integer score) do not burn it. Games must therefore run at least `minDurationMs` of real time (default `pour` 8000 ms, `cheers` 10000 ms) and never exceed `maxScore` (`pour` 500 = 5 glasses x 100, `cheers` 1000 = 10 taps x 100).
Coupon rule: score >= reward `threshold`, stock left, and this table+seat has not already received that reward.

### `POST /api/t/<token>/calls` — body `{ "type": "물" }`
(**New:** 429 `too_many_calls` — at most 50 calls per table seat in total, resolved ones included.)
`type` in `물`, `수저`, `치워주세요`, `기타`. 200 `{ "call": { id, type, createdAt }, "duplicate": false }`; `duplicate: true` if the same type is already open for this table. 400 `bad_call` (`allowed`).

### `GET /api/t/<token>/events` — SSE, see section 7.

**Board snapshot**
```json
{ "hour": { "start": 1731478800000, "end": 1731482400000, "awarded": false,
            "ranking": [ { "table": 4, "score": 1650, "games": { "pour": 450, "cheers": 1200 }, "nick": "맥주왕" } ] },
  "prevHour": { "start": 0, "winner": { "table": 4, "score": 1650, "games": {}, "nick": "..." } , "awarded": true },
  "hourly": { "enabled": true, "label": "안주 1개 서비스", "type": "item", "amount": null, "item": "안주 1개" },   // staff-editable; `enabled: false` = no hourly award
  "games": { "pour": [ { "rank": 1, "table": 4, "nick": "맥주왕", "score": 450 } ], "cheers": [ ... ] },
  "gameInfo": { "pour": { "label", "maxScore", "minDurationMs" }, "cheers": {...} },
  "rewards": [ { "id": "drink", "label": "음료 1잔", "remaining": 16, "stock": 20 } ],   // stock left per reward; only these 4 fields
  "notice": { "text", "level" } | null }   // H9 staff banner: in `GET /api/board` and in every `state` event of `/api/board/events` (read it from here, not from the URL)
```
`hour.ranking` = top 5 tables of the current clock hour (table score = sum over games of the table's best score in that hour). `prevHour.winner` is `null` if nobody played. `games.<id>` = top 10 tables by best score all event long (`nick` may be `null`; show "N번 테이블"). **Refund** (H6): `{ id, orderId, table, updatedAt, amount, reason: "cancelled|overpaid|edit_lower_total|legacy_cancelled", createdAt, doneAt: null | epoch ms, method: "transfer|cash|other"|null, note: string|null }`. `updatedAt` = the refund's ORDER `updatedAt` (send it back as `expectedUpdatedAt`). `legacy_cancelled` = money received on an order that Release 1 cancelled (no refund tracking then): its `createdAt` is the cancellation time, and staff must check whether it was already handed back by hand. ### Order actions
**Dry-run preview (`dryRun: true`):** `POST /api/staff/orders/<id>/items`, `/service`, `/paid` and `POST /api/staff/tables/<n>/orders` accept `"dryRun": true` (literal true only). The server runs the real code in a transaction that is rolled back and answers `{ "dryRun": true, "order": Order }` (for order creation also `duplicate`) — exactly what the real call would return: new lines, `subtotal`, `memberDiscount`, `couponDiscount`, `total`, `balanceDue` / `refundDue` / `overpaid`, `paid`. The same validation applies, so problems come back as the real errors (e.g. 409 `insufficient_stock`, `sold_out`, `stale`, 400 `no_lines`). **Nothing is written:** no audit row, no stock change, no `updatedAt` bump, no SSE (state is byte-identical before and after). Times in the preview (`updatedAt`, `paidAt`, `createdAt`) are not those of a later real call.
Every action below re-reads the order inside its transaction. **H15 — `expectedUpdatedAt` (optional integer, the order's `updatedAt` the client rendered):** when given and different from the current value nothing is applied and the server answers **409 `stale`** `{ error, message, order: <current Order> }` — show the fresh order and let the staff member retry. Omitted = no check (old behaviour). A non-integer -> 400 `bad_expected`. Accepted by `status`, `paid`, `items`, `service`, `move` and `refunds/<id>/done` (checked against the refund's order).
- `POST /api/staff/orders/<id>/status` body `{ "status": "pending|cooking|served|cancelled", "expectedUpdatedAt"? }` -> `{ order }`. Any change between the first three is allowed (undo a mis-tap); accept = `cooking`, done = `served`. `cancelled` restores an applied discount coupon and the stock (H10) and is terminal (409 `order_cancelled` afterwards); **money already received on a cancelled order becomes a refund entry (H6)**. 400 `bad_status`, 404 `no_order`, 409 `stale`.
- `POST /api/staff/orders/<id>/paid` body `{ "paid": true, "method"?: "transfer|cash|other", "amount"?: won, "expectedUpdatedAt"? }` -> `{ order }` (**H5**). `paid: true` ADDS a payment of `amount` (default: the remaining balance = `balanceDue`, i.e. `total − (paidAmount − refundedAmount)`; so after a refund was paid out and the order grew again, a bare `{ paid: true }` settles it in one call; `method` default `transfer`): the order becomes `paid: true` once the money held covers `total`; less leaves it unpaid with a `balanceDue`; more records `overpaid` and opens a refund entry for the excess. `paidBy` is `"staff"`. A second `paid: true` WITHOUT `amount` on an already fully paid order is refused with **409 `stale`** (a double tap from another phone must never double-apply); with an explicit `amount` it adds the money. `paid: false` removes every payment of the order (clears `paidAmount`/`paidMethod`/`paidAt`, deletes open refund entries, hands EVERY deposit notice linked to the order back to `pending`); refused with **409 `has_refunds`** once any refund of the order was paid back. 400 `bad_paid`, `bad_method`, `bad_amount` (integer 0..10,000,000; 0 only for free orders), 409 `order_cancelled`, 409 `stale`.
- **`POST /api/staff/tables/<n>/orders` (H1)** body `{ "key": "<8-64 chars>", "items": [ { "id", "qty" } ], "note"?, "depositor"?, "allowHidden"?: true, "accept"?: true }` -> 201 `{ order, duplicate: false }` / 200 `{ order, duplicate: true }`. Staff create an order for a table's current seat (phone / paper orders). Same validation as guests (`bad_key`, `bad_items`, `bad_qty`, `dup_item`, `too_many_lines`, `unknown_item`, `sold_out`, `insufficient_stock`, `bad_note`, `bad_depositor`), plus: **no member discount and no coupon** (`couponCode` -> 400 `coupon_not_allowed`), **allowed while ordering is closed**, never needs `depositor`, `createdBy: "staff"`, the order cap is **80** per seat (guests: 40) -> 429 `too_many_orders`. `accept: true` = staff accepts it at once: the order is created already `cooking` (it appears in the kitchen, kitchen SSE `new_cooking`, and its guests get `order_status`); without it the order is `pending` and goes through the normal accept step. **Response:** `{ "order": Order, "duplicate": false }` with HTTP 201 for a new order, `{ order, duplicate: true }` with 200 for a replayed `key`. The order has `createdBy: "staff"` and no member discount. Idempotent by `key` per table+seat. Hidden items are refused (`unknown_item`) unless `allowHidden: true` (then they are not sold-out checked either). 404 `no_table`.
- **`POST /api/staff/orders/<id>/items` (H2)** body `{ "items": [ { "id", "qty": 0..20, "service"?: true } ], "expectedUpdatedAt"? }` -> `{ order }`. REPLACES the order's normal lines with the listed ones (a line not listed is removed; `qty: 0` also removes it; at least one normal line must remain: 400 `no_lines`, cancel the order instead). **Lines already on the order keep their original name and unit price; only lines added now use the current menu price.** Free service lines are kept unless listed. The member discount is recomputed from the rule stored on the order (`memberRule`), a coupon on the order becomes `min(coupon amount, remaining)`, the total never goes below 0. Payments are kept: if the order was paid and the new total is lower it stays `paid` with `overpaid`/`refundDue` and an open refund entry; if higher it becomes `paid: false` with a `balanceDue`. Stock follows the change in quantity (reducing gives stock back, adding takes it: 409 `insufficient_stock`). Errors: 400 `bad_items`, `bad_qty`, `dup_item`, `unknown_item`, `no_lines`; 404 `no_order`; 409 `order_cancelled`, `sold_out` (only when the quantity of a sold-out item grows), `insufficient_stock`, `stale`. Allowed in any non-cancelled status (including `served`).
- **`POST /api/staff/orders/<id>/service` (H3)** body `{ "itemId": "cola", "qty": 1..20, "expectedUpdatedAt"? }` -> `{ order }`: adds a free service line (`unitPrice` 0, `service: true`; repeating it for the same item accumulates, at most 20 per item). Totals do not change. It uses the item's stock like a normal line, shows in the kitchen (`items[].service`) and in sales (`byItem[].serviceQty`). 400 `bad_qty` / `bad_items`, `unknown_item`; 409 `sold_out`, `insufficient_stock`, `order_cancelled`, `stale`; 404 `no_order`.
- **`POST /api/staff/orders/<id>/move` (H4)** body `{ "to": 5, "expectedUpdatedAt"? }` -> `{ order, from }`: moves ONE order to the current seat of table `to`. **The coupon applied to it is NOT moved:** the coupon stays recorded as earned by its original table+seat (so that seat cannot earn the reward again and stock stays right) and stays tied to the order; if the order is cancelled, the restored coupon returns to the seat that earned it; its idempotency key is rewritten (`<key>~m<id>`) so equal keys never collide; the source table's guests and the target table's guests both get the update. 400 `bad_tables`, `same_table`; 404 `no_table` / `no_order`; 409 `order_cancelled`, `stale`.
- **`POST /api/staff/refunds/<id>/done` (H6)** body `{ "amount": integer (REQUIRED), "method"?: "transfer|cash|other" (default cash; recorded and summed in `byMethod.refunded`), "note"?: 1..60 chars, "expectedUpdatedAt"? }` -> `{ ok, refund }`: staff handed the money back. **`amount` must equal the entry's CURRENT amount** (what the staff member saw and handed over); if a concurrent edit changed it: **409 `refund_changed`** `{ refund: <current entry> }` and nothing is recorded. 400 `bad_amount` (missing / not a positive integer), `bad_method`, `bad_note`; 404 `no_refund`; 409 `refund_done`, `stale`.

### Menu management (new)
The menu is stored in the database. On the very first boot (empty menu tables, also when upgrading an older database) it is seeded once from `menu.json` and a `menu_seeded` flag is stored; after that the database is the source of truth and `menu.json` is never read again — not even if staff later delete every item and category, and not after a reset. All endpoints below need the staff session, same-origin and JSON; success responses are `{ ok: true, menu: <staff menu view>, item?: <staff item>, category?: { id, name } }` (re-render from `menu`). Every edit is pushed over SSE to guests and staff.
Rules: item `name` 1..30 characters after control/invisible-character stripping (zero-width, bidi, Hangul fillers) and trimming, must contain at least one visible character (else 400 `bad_name`), stored exactly as typed (trimmed, inner whitespace collapsed), and unique among all items **on a normalised key** (NFKC, collapsed whitespace, case-insensitive: "Beer", "beer" and fullwidth "Ｂｅｅｒ" are the same name -> 409 `name_taken`; same rule for category names, and an item sent with `category: "dessert"` goes into the existing "Dessert" category); `price` integer 0..1,000,000 and a **multiple of 100**; `desc` 0..60 characters; category name 1..12 characters, unique; at most **100 items** and **12 categories**. Hidden items are not shown to guests and cannot be ordered (400 `unknown_item`, same as a nonexistent id); sold-out items are shown greyed and cannot be ordered (409 `sold_out`).
- `POST /api/staff/menu/items` body `{ "name", "price", "category": "안주", "desc"?: "", "hidden"?: false }` (**new `hidden`**: create an item already hidden so guests never see it; non-boolean -> 400 `bad_hidden`) -> `{ ok, item, menu }`. `category` is a category NAME; it is created if missing. 400 `bad_name` / `bad_price` / `bad_desc` / `bad_category`, 409 `name_taken` / `too_many_items` / `too_many_categories`.
- **H10 — stock counter:** `POST /api/staff/menu/items` and `POST /api/staff/menu/items/<id>` also accept `"stockLeft": integer 0..9999 | null` (`null` = unlimited; others -> 400 `bad_stock_left`). Every order (guest or staff, including service lines and staff edits) takes from it inside the order transaction (409 `insufficient_stock`, nothing created); reaching 0 sets `soldOut: true` AUTOMATICALLY (`stockAuto: true`); cancelling an order or reducing a line gives the stock back and lifts ONLY an automatic sold-out; a sold-out toggled by hand (`/soldout`) is never lifted by the counter. Setting `stockLeft: 0` by hand is an automatic sold-out too, raising it (or `null`) lifts it. `reset` / day close keep the numbers and clear the sold-out flags, except that an item whose count is 0 stays (automatically) sold out until staff raise the count.
- `POST /api/staff/menu/items/<id>` body: any of `{ "name", "price", "category" (name), "desc", "hidden": boolean, "sortOrder": integer 0..100000, "stockLeft" }` -> `{ ok, item, menu }`. 400 `nothing_to_update` (empty body), `bad_hidden`, `bad_sort` and the validation codes above, 404 `no_item`, 409 `name_taken` / `too_many_categories`. Moving an item to another category never deletes the old category.
- `POST /api/staff/menu/items/<id>/delete` body `{}` -> `{ ok, menu }`. **409 `in_use`** when the item was ever ordered since the last reset: hide it instead. 404 `no_item`.
- `POST /api/staff/menu/reorder` body `{ "items"?: [ "<itemId>", ... ], "categories"?: [ <categoryId>, ... ] }` -> `{ ok, menu }`. Each listed id's `sortOrder` becomes its index in the list (send the complete list in the desired order; guests see categories in category order and items by sort order within their category). 400 `bad_reorder` (not a list / duplicates / non-ids), 404 `no_item` (unknown id).
- `POST /api/staff/menu/categories` body `{ "name" }` -> `{ ok, category: { id, name }, menu }`. 400 `bad_category`, 409 `name_taken` / `too_many_categories`.
- `POST /api/staff/menu/categories/<id>` body `{ "name" }` (rename) -> `{ ok, category, menu }`. 404 `no_category`, 409 `name_taken`.
- `POST /api/staff/menu/categories/<id>/delete` body `{}` -> `{ ok, menu }`. **409 `category_not_empty`** while it still holds items (hidden ones count); 404 `no_category`. Empty categories are not removed automatically (staff delete them), but guests never see a category without visible items.
- Existing `POST /api/staff/menu/<itemId>/soldout` now returns the staff menu view in `menu`.

### Reward management
Rewards live in the database (seeded once from `rewards.json`, which is never read again for rewards afterwards; an invalid file logs `rewards.json is invalid: …` and starts with no rewards). Games (`pour`, `cheers`) with `maxScore` / `minDurationMs` stay read-only constants. At most 12 rewards.
**Reward**: `{ id, label, game: "pour"|"cheers", threshold, type: "discount"|"item", amount: won|null, item: string|null, stock, issued, remaining, used, active }` — `stock` = configured total, `issued` = coupons handed out, `remaining = stock - issued`, `used` = redeemed or applied coupons. New ids look like `r` + 8 hex; seeded ones keep their ids.
Rules: `label` 1..20 visible characters; `game` one of the games; `threshold` integer 0..that game's `maxScore`; `type` `discount` needs `amount` (integer, multiple of 100, 100..100000), for `item` any `amount` is ignored (stored null; the coupon's `item` text is the label); `stock` integer 0..10000; `active` boolean (default true on create).
- `GET /api/staff/rewards` -> `{ rewards: [Reward], hourly, games }` (the same data is in staff `state`).
- `POST /api/staff/rewards` body `{ label, game, threshold, type, amount?, stock, active? }` -> `{ ok, reward, rewards }`. 400 `bad_label` / `bad_game` / `bad_threshold` / `bad_type` / `bad_amount` / `bad_stock` / `bad_active`, 409 `too_many_rewards`.
- `POST /api/staff/rewards/<id>` body: any of `label, game, threshold, type, amount, stock, active` -> `{ ok, reward, rewards }`. 400 `nothing_to_update` and the codes above, 400 `stock_below_issued` (`issued` in payload; stock may equal issued, never be lower), 404 `no_reward`. Changing `type` to `discount` needs an `amount`. **Edits only affect coupons issued afterwards:** every coupon stores its own label, type and amount at issue time, and applying/redeeming uses those stored values.
- `POST /api/staff/rewards/<id>/delete` body `{}` -> `{ ok, rewards }`. 409 `in_use` if anything was ever issued (deactivate instead); 404 `no_reward`.
- `POST /api/staff/rewards/<id>/stock` (older endpoint, still works) body `{ "stock": n }` -> `{ ok }`; same rules.
- **Inactive** (`active: false`) rewards are hidden from guests and the board and are never issued; coupons already issued stay valid. Several rewards may target the same game: one play can earn each of them, but each reward at most once per table seat.
- Reward edits are pushed live (guest, board and staff SSE).
- **Hourly ranking reward:** `POST /api/staff/hourly-reward` body any of `{ "label": 1..20 chars, "type": "item"|"discount", "amount": 100..100000 step 100 (required when type is discount), "enabled": boolean }` -> `{ ok, hourly: { enabled, label, type, amount, item } }`; 400 `nothing_to_update` / `bad_label` / `bad_type` / `bad_amount` / `bad_enabled`. `POST /api/staff/award-hour` issues a coupon of that type/amount/label and now answers **409 `hourly_disabled`** while `enabled` is false. The same object is `hourly` in staff state and the board snapshot.

### Payment settings
- `POST /api/staff/pay` body: any subset of `{ "bank": 1..20 chars, "account": digits and hyphens, 8..20 digits (`110-123-456789`; no leading/trailing/double hyphen), "holder": 1..20 chars, "tossEnabled": boolean, "kakaoPayUrl": "" | "https://qr.kakaopay.com/<path>", "requireDepositor": boolean, "confirmAccount": "..." }` -> `{ ok, pay: { bank, account, holder, tossEnabled, kakaoPayUrl, requireDepositor, changedAt } }`. Nothing is applied unless every sent field is valid. **Changing `bank`, `account` or `holder` requires `confirmAccount` equal to the resulting account number (hyphens ignored)** — the staff UI makes the user type the account twice: otherwise 400 `account_mismatch`. `kakaoPayUrl` must be `https`, hostname exactly `qr.kakaopay.com`, no credentials/port, with a path, max 200 chars (else 400 `bad_kakao_url`; stored normalised; `""` clears it). `changedAt` records the last bank/account/holder change. Other 400 codes: `nothing_to_update`, `bad_bank`, `bad_holder`, `bad_account`, `bad_toss_enabled`, `bad_require_depositor`. The first boot seeds the settings from env `PAY_BANK/PAY_ACCOUNT/PAY_HOLDER`, afterwards the database wins. Guests receive everything except `changedAt` (`pay` in the guest snapshot). `reset` keeps the settings.

### Deposit notices (semi-automatic payment confirmation)
A phone (SMS forwarder / automation app) sends every bank deposit text to the booth; matching an order is conservative.

**Auto-confirm is OFF by default (fresh installs, and forced off once on every existing database).** Why: the name printed in a bank SMS is typed by the *sender*, so every character of the notice is attacker-controlled, and a name + amount match can be guessed or gamed. With auto-confirm off the hook still receives and parses every notice; staff see each one as `pending` with `reasons` (for a perfect notice: `["auto_off"]`) and the candidate orders, and confirm with one tap (`assign`). Staff may switch auto-confirm on (`autoConfirm: true`), and even then it only fires for amounts up to `autoConfirmMaxAmount` (default **30,000** won) and only when every rule below holds; anything doubtful stays manual.
- **Webhook URL staff copy:** `GET /api/staff/deposit-hook` -> `{ secret, path, url, header, headerUrl }` where `url` = `<PUBLIC_ORIGIN><BASE>/api/deposit-hook/<64 hex secret>`, e.g. `https://coms.kw.ac.kr/booth/api/deposit-hook/3f9c…(64 hex)…a1`. `POST /api/staff/deposit-hook/rotate` body `{}` -> `{ ok, secret, path, url, header, headerUrl }` makes a new secret ("재발급"); the old URL stops working at once. The secret is generated once and kept across restarts and resets; it is never sent to guests.
- **Secret in a header instead of the URL (new):** `POST <BASE>/api/deposit-hook` with the header `X-Booth-Hook: <secret>` (`headerUrl` = `<PUBLIC_ORIGIN><BASE>/api/deposit-hook`, `header` = `X-Booth-Hook`) behaves exactly like the path form, so the secret need not appear in any URL / access log. Both forms stay valid; rotation invalidates both.
- **The hook itself:** `POST <BASE>/api/deposit-hook/<secret>`, no session, no Origin / same-origin check (the secret in the path is the credential, compared in constant time). Body: JSON `{ "text": "..." }` (`Content-Type: application/json`) or the raw text (`Content-Type: text/plain`), max 2 KB (413; other types 415; bad JSON 400 `bad_json`; no `text` string 400 `bad_body`). A wrong secret answers `404 { error: "not_found" }` after a fixed 300 ms delay; wrong-secret attempts have their own budget (20 per minute and at most 20 delayed at a time, the rest answer immediately) and never consume the real forwarder's 60 per minute. Requests with the right secret count toward the 60 per minute only once they are well-formed. At most 60 accepted notices per minute server-wide (429 `rate_limited`; also 429 `queue_full` when 1500 notices already wait for staff — `hookRateLimited` is set for both). Answer: `{ ok: true, status, id? }` with `status` one of `matched`, `pending`, `review`, `unparsed`, `duplicate` (an identical normalised text less than 5 seconds after the previous one = a forwarder retry: dropped, nothing stored — the only silent drop) or `ignored` (stored for staff but never matchable, see Parsing). Stored notices also return their `id`. It never reveals which order matched.
- **Parsing (security note: the sender controls the name printed in the SMS, so every character is untrusted).** A text without `입금` is `ignored` (withdrawals, ads). A text that contains `입금` AND a reversal/correction/withdrawal word (`출금` — but not inside `입출금` such as KakaoBank's 입출금통장 —, `취소`, `정정`, `오류`, `반환`, `실패`, or `입금` directly followed by `계좌`/`취소`/`은행`/`예정`/`한도`), or is longer than 300 characters (`text_too_long`), gets status **`review`**: counted in the pending badge, assignable only with `force: true`, never automatic (so a real deposit from 정정훈 is not lost). Otherwise the text is normalised (NFKC: full-width digits become ASCII; U+2028/U+2029 become spaces), masked account fragments, dates and times are removed as whole tokens, and **a balance is removed only when `잔액 <number>` STARTS a line** (a sender-typed "잔액" in the middle of a line can never hide the real amount); the remaining amount-shaped numbers are counted. **A notice is `autoEligible` only if exactly ONE amount-shaped number remains (100..10,000,000), exactly ONE name token remains that is 2..10 Hangul/Latin letters (no digits, no `원`, `,`, `.`), and the name and the amount are on different lines or separated by the literal word `입금`** (otherwise `amount_adjacent_to_name`: single-line SMS such as `홍길동님이 16,000원을 입금했습니다` are display-only). Bank names and template words (스마트폰뱅킹, 입출금통장, 통장, From, 모바일 …) are skipped. Not eligible notices carry `reasons` (`multiple_amounts`, `no_amount`, `amount_range`, `no_name`, `name_has_digit`, `name_shape`, `several_names`, `amount_adjacent_to_name`, `text_too_long`); a best-guess amount is still stored for display with `amountGuessed: true` ("추정 금액"). A deposit text with no amount at all is `unparsed`. The raw text (max 300 chars) is kept for staff.
- **Matching** (in one transaction): candidates are non-cancelled, **unpaid** orders in the **current seat of a table within the table count** (orders of a cleared seat or a hidden table are invisible to staff and are never matched; manual assign/attach is limited to the same orders, others answer 404 `no_order`) whose **balance** (`total − money held`) equals the notice amount and is above 0 (so 3,000 cash + a 5,000 transfer for an 8,000 order matches cleanly; candidate objects carry `total` and `balance`), created in the last 6 hours. Automatic confirmation (only when `autoConfirm` is on) needs ALL of: the notice is `autoEligible`; (a) exactly ONE candidate exists (orders with and without a depositor name both count); (b) that order has a depositor name; (c) **the names are equal** after NFKC / spaces removed / lower-casing (no prefix or truncation rule); **no visible order of the last 6 hours with the same total was already marked paid BY HAND without a notice** (`paid_by: "staff"`, no notice attached: the transfer may belong to it — `maybe_already_handled`; orders paid by an earlier notice do not count); the amount is not above `autoConfirmMaxAmount` (default 30,000; 0..1,000,000; 0 = never); and the same normalised text was not seen in the last 6 hours (`duplicate`). Otherwise the notice stays `pending` with `reasons`. Automatic confirmation = marking the order paid with `paidBy: "auto"` (guests get the normal paid update; staff get `deposit_matched` with `{ id, status, orderId, table }`). A notice is linked to at most one order and an order to at most one notice.
- **Reason codes** (`reasons` on a notice or on a test result; empty on a matched notice): `multiple_amounts`, `no_amount`, `amount_range`, `no_name`, `name_has_digit`, `name_shape`, `several_names`, `ignore_word` (status `review`), `duplicate`, `auto_off`, `over_max_amount`, `maybe_already_handled`, `no_candidate`, `several_candidates`, `no_depositor_on_order`, `name_mismatch`, `amount_adjacent_to_name`, `text_too_long`.
- `GET /api/staff/deposits` -> `?before=<id>&limit=<1..200, default 200>` (integers, else 400 `bad_query`) -> `{ notices: [Notice] (newest first), next: <id> | null (pass as `before` for the next page), pending, unparsed, ignored, review, autoConfirm, autoConfirmMaxAmount }`. **The staff `state` does NOT embed the notice list:** it has the counts (`deposit`) and `depositNotices` = the newest **50 OPEN** notices (`pending` / `review` / `unparsed`); fetch the rest here. Worst case measured (380 orders, 200 pending notices against 190 same-total orders): staff state about 278 KB, this endpoint's 200-notice page about 261 KB. **Notice**: `{ id, receivedAt, text, amount|null, amountGuessed: boolean, depositor|null, status: "pending"|"matched"|"unparsed"|"review"|"ignored"|"dismissed", orderId|null, matchedAt|null, matchedBy: "auto"|"staff"|null, repeatCount: number, lastAt: epoch ms, reasons: [code], candidates: [ { id, table, total, balance, depositor, createdAt } ] (at most 10), candidateCount, handledOrders: [ same shape ] (at most 10), handledCount }` (`candidates` = live unpaid orders whose balance equals the amount and `handledOrders` = live orders with that amount that staff already marked paid by hand without a notice; both only for `pending`).
- `POST /api/staff/deposits/<id>/assign` body `{ "orderId": 12, "force"?: true, "note"?: "..." }` -> `{ ok, notice, order }` (order `paidBy: "staff"`, `paidMethod: "transfer"`, the notice amount is added to the order's `paidAmount`: less than the total leaves a `balanceDue`, more opens a refund for the excess). **H5: a forced mismatch (amount differs, or the notice has no amount) needs `note`** (1..60 characters after cleaning) -> else 400 `note_required`; the note is kept in the audit log. Works for `pending`, `unparsed` and `review` notices; **`review` notices always need `"force": true`** (409 `review_needs_force`). 409 `amount_mismatch` (`noticeAmount`, `orderTotal`, `orderBalance`; compared with the order's BALANCE; also when the notice has no amount) unless the literal `"force": true` (then `note` is required and an amount above the balance opens a refund entry); 409 `notice_closed`, 409 `order_paid` (use attach), 409 `order_cancelled`, 400 `bad_order`, 404 `no_notice` / `no_order`.
- **New — `POST /api/staff/deposits/<id>/attach`** body `{ "orderId": 12, "force"?: true, "note"?: "..." }` (a forced mismatch needs `note`, 400 `note_required`) -> `{ ok, notice, order }`: links a notice to an order that staff ALREADY marked paid by hand, **without changing its payment state** (the notice becomes `matched`, `matchedBy: "staff"`). For the `maybe_already_handled` case (`handledOrders`). Errors: 409 `order_unpaid` (use assign), 409 `order_has_notice`, 409 `notice_closed`, 409 `order_cancelled`, 409 `amount_mismatch` / `review_needs_force` (force), 400 `bad_order`, 404 `no_notice` / `no_order`. Undoing the order's payment later returns the notice to `pending`.
- **Repeated texts collapse:** an identical normalised text within 6 hours of an earlier OPEN notice (`pending`, `review`, `unparsed`, `ignored`) does not create a row: it increments that row's `repeatCount` and sets `lastAt` (staff still get a `new_deposit` event with `repeatCount`). A repeat arriving less than 5 seconds after the previous one is a forwarder retry and is dropped without counting (`status: "duplicate"`). If the earlier notice is already `matched` or `dismissed`, the repeat becomes a new `pending` row with reason `duplicate`. A repeated text is never auto-confirmed (e.g. the same payer paying a second order with a forwarder that sends no time or balance): staff assign or dismiss it and see the repeat count. `ignored` notices cannot be assigned or dismissed (409 `notice_closed`); show them in a collapsed list.
- Housekeeping: `dismissed` / `ignored` rows beyond the newest 2000 are pruned; **matched notices are never pruned**. The waiting queue (`pending`, `review`, `unparsed`, `ignored`) is capped at 1500 rows: when full, the oldest `unparsed` row (then the oldest `ignored` row) is dropped to make room; `pending`, `review` and `matched` rows are never evicted. Only if nothing can be evicted does the hook answer 429 `queue_full` (and `hookRateLimited` becomes true).
- `POST /api/staff/deposits/<id>/dismiss` body `{}` -> `{ ok, notice }` (`pending`/`unparsed`/`review` only; 409 `notice_closed`).
- `POST /api/staff/deposits/autoconfirm` body: `{ "autoConfirm"?: boolean, "autoConfirmMaxAmount"?: integer 0..1000000 }` (at least one) -> `{ ok, autoConfirm, autoConfirmMaxAmount }` (400 `bad_auto_confirm`, `bad_auto_max`). Off = every notice stays `pending` for one-tap assignment. Defaults: **off**, ceiling **30,000** won (amounts above it are never auto-confirmed).
- **Test mode ("테스트 보내기"): `POST /api/staff/deposit-hook/test`** body `{ "text": "..." }` (staff session, same-origin, JSON, text max 2 KB) -> `{ parsed: { kind, amount, name, autoEligible, reasons }, wouldMatch: { status, reasons, orderId?, candidates: [...], handledOrders: [...] } }`. It runs the real parser and matcher but **stores nothing and changes nothing** (no notice, no order marked paid). The staff UI must use this endpoint for its test button, never the public hook. 400 `bad_body`.
- **Undo:** `POST /api/staff/orders/<id>/paid { "paid": false }` on an automatically confirmed order marks it unpaid again and returns its notice to `pending`. Marking an order paid manually sets `paidBy: "staff"` and does not link a notice.
- Staff `state.deposit` carries the counts; staff SSE sends `new_deposit` / `deposit_matched`. Notices and the secret are never exposed to guests. `reset` deletes the notices but keeps the secret and the payment settings.

### Sales
- `GET /api/staff/sales` ->
```json
{ "totals": { "orders": 40, "billed": 400000, "revenue": 380000, "paidAmount": 395000, "refundsDone": 15000, "refundDue": 8000,
              "paidRevenue": 360000, "unpaidRevenue": 30000, "writtenOff": 12000,
              "discount": 5000, "memberDiscount": 3200, "memberOrders": 11 },
  "byMethod": { "transfer": { "received": 250000, "refunded": 3000, "net": 247000, "count": 31 }, "cash": { ... }, "other": { ... } },
  "byHour": [ { "hour": 1731478800000, "label": "2026-11-13 18:00", "orders": 12, "billed": 100000, "revenue": 90000, "discount": 1000 } ],
  "byItem": [ { "id", "name", "qty", "serviceQty", "gross" } ],
  "coupons": [ { "rewardId": "d1000|hour|staff", "label", "type", "issued", "used" } ],
  "unpaid": [ { "orderId", "table", "total", "paidAmount", "balance", "updatedAt" } ],   // open unpaid orders (not written off); paidAmount = money held; updatedAt = the order's, to send as expectedUpdatedAt
  "writtenOff": [ { "orderId", "table", "total", "paidAmount", "balance", "writtenOffAt", "updatedAt" } ],
  "refunds": [ Refund ] }
```
**`byMethod`**: per payment method, `received` = sum of the payments recorded with that method (every payment is ledgered with its own method: cash 3,000 then transfer 5,000 gives cash 3,000 / transfer 5,000), `refunded` = refunds already handed back with that method, `net = received - refunded`, `count` = number of payments. **Σ `net` over the three methods = `totals.revenue`** and Σ `received` = `totals.paidAmount`. Orders from Release 1 are backfilled (hand-confirmed = `other`, automatic = `transfer`); the same object is in every day report and the CSV (section 결제수단별).
**Exact semantics (Release 2 — these changed):**
- `revenue` = **money actually received minus refunds already handed back** = `paidAmount - refundsDone`. `paidAmount` = sum of `paidAmount` over ALL orders (cancelled ones included: their money was received until it is refunded). It never counts unpaid balances.
- `refundDue` = open refund entries (money owed back, not yet handed back). While a refund is open the money still counts in `revenue`; marking it done (`refunds/<id>/done`) moves it into `refundsDone` and lowers `revenue`.
- `writtenOff` (미수금) = balances of unpaid, non-cancelled orders whose table was force-cleared; **never part of `revenue`**; an order leaves this list when it is paid later (its money then counts in `revenue`) or when the clear is undone.
- `billed` = sum of `total` of non-cancelled orders (what was charged, after discounts), the old "revenue" meaning. `unpaidRevenue` = balances of non-cancelled, unpaid, not written-off orders (still open at tables). `paidRevenue` = money received on non-cancelled orders. `orders`, `discount`, `memberDiscount`, `memberOrders` count non-cancelled orders as before.
- `byHour[].billed` / `.revenue` follow the same split, by the hour the order was created; `byItem` ignores cancelled orders; `qty` excludes service lines (`serviceQty`), `gross` is before discounts and excludes service lines.
Covers every seat since the last reset / day close. `label` is KST.
- `GET /api/staff/sales.csv` -> `text/csv; charset=utf-8` attachment `booth-sales.csv`, starts with a UTF-8 BOM, sections: 요약, 시간대별 매출, 메뉴별 판매, 쿠폰, **미수금**, **미결제(진행중)**, **환불**. Text cells that start with `=`, `+`, `-` or `@` get a leading `'` (spreadsheet formula injection). Use a plain link / `location.href`, it is a normal GET with the cookie.
- `POST /api/staff/reset` body `{ "confirm": "초기화" }` -> `{ ok }`. **Deletes:** orders, coupons, plays, nicknames, calls, waitlist, **deposit notices, refunds, table-clear history**, and the waitlist switch (re-opens) and the notice banner. **Resets:** seats to 1, ordering open, sold-out flags, and every reward's `issued` count to 0 (so `remaining` returns to the configured `stock`). **Keeps:** table tokens and the table count; the payment settings and the deposit-hook secret; the menu (items, prices, hidden flags, categories, photos, stock numbers); the reward definitions (label, game, threshold, type, amount, active flag, configured `stock` — including any stock changes staff made) and the hourly reward setting; the member-discount settings; **the audit log and the day reports**. A backup copy is taken right before the wipe (the server first waits for any backup already running, then takes its own). 400 `confirm_required`. `reset` makes NO report (it is for rehearsal data).
- **H14 — `POST /api/staff/day/close`** body `{ "confirm": "마감", "force"?: true }` -> `{ ok, report: { id, label, totals } }`. **Without the literal `force: true`:** 409 `nothing_to_close` when there is no order at all, and 409 `open_items` `{ refundDue: { entries, amount }, unpaid: { orders, amount }, unserved: { orders }, writtenOff: { orders, amount }, pendingNotices: { count, amount } }` when anything is still open (`pendingNotices` = deposit notices staff never confirmed or dismissed) (show these numbers, then resend with `force: true`); nothing is changed and no backup is made in either case. A forced report itemises everything: its `refunds` (open ones have `doneAt: null`), `unpaid` (open unpaid orders: `{ orderId, table, total, paidAmount, balance }`) and `writtenOff` lists, `forced: true`, `pendingNotices` (`[ { id, receivedAt, amount, status } ]`, never the SMS text), and the CSV has the sections 미결제(진행중), 미수금, 환불 and 미확인 입금 알림. Otherwise: ends the business day. A backup copy is taken first, then in one transaction the full sales summary (the `GET /api/staff/sales` JSON plus `generatedAt`) is frozen into a report and the day's data is wiped exactly like `reset` (same keeps list). `label` = KST date of the first order (or today). 400 `confirm_required` (any other word, including "초기화").
- `GET /api/staff/day/reports` -> `{ reports: [ { id, label, createdAt, totals } ] }` newest first. `GET /api/staff/day/reports/<id>` -> `{ id, label, createdAt, generatedAt, forced, totals, byHour, byItem, coupons, unpaid, writtenOff, refunds }` (frozen; never changes). `GET /api/staff/day/reports/<id>.csv` -> the same CSV as `sales.csv` for that report (UTF-8 BOM, `booth-day-<id>.csv`). 404 `no_report`.

### Boot self-heal (rollback safety)
Older code (a roll-back to Release 1 and forward again, or a crash mid-migration) writes only the `paid` flag. On every boot the server trusts the flag wherever it contradicts the money recorded, then repairs the payment ledger: (a) paid but money held < total -> `paidAmount` is raised to cover the total (method `other`); (b) unpaid but money held >= total -> `paidAmount` is reset to what was refunded, so the full balance is due again; (c) cancelled while paid -> `paidAmount` = total and a refund entry (`legacy_cancelled`, dated with the cancellation) is created. Idempotent; one audit row `migrated` (`1차 버전 데이터 보정 · 주문 N건 ...`) is written only when something changed.

### Audit log (H13)
- `GET /api/staff/audit?before=<id>&limit=100` (both optional non-negative integers; anything else -> 400 `bad_query`) -> `{ entries: [ { id, at, action, target, summary, summaryKo } ], next: <id> | null }` — **`summaryKo`** is a Korean sentence staff can read as is (e.g. `주문 #12 입금 확인 · 현금 5,000원 · 잔액 3,000원`, `3번 테이블 강제 정리 · 미수금 1건 8,000원`, `메뉴 품절 표시`), present on every row (rows written before this field fall back to `summary`); `summary` / `target` stay the machine-readable English text. Never any secret in either, newest first (`limit` 1..200, default 100; pass `next` as `before` for the next page; `null` = end). The newest **5000** rows are kept; `reset` / day close keep them. Recorded actions (`action`): `order_create_staff`, `order_status` (accept / served / undo, `from→to`), `order_paid`, `order_unpaid`, `order_cancel`, `order_edit`, `order_service`, `order_move`, `table_clear`, `table_unclear`, `table_move`, `refund_done`, `coupon_manual`, `coupon_void`, `coupon_redeem`, `deposit_assign`, `deposit_attach`, `deposit_dismiss`, `deposit_auto`, `menu_create`, `menu_update` (price / name / hidden / stock), `pay_settings`, `member_discount`, `notice` (old → new text), `ordering` (`true→false`), `table_count` (`40→30`), `table_rotate`, `deposit_secret_rotate`, `deposit_auto_setting` (`autoConfirm false→true, max 30000→20000`), `wait_timeout` (`5→7 min`), `reset`, `day_close`, `login`, `lockout`, `migrated` (boot self-heal, see below), and `staff_action` for the other staff writes (target = the endpoint with ids as `#`, summary = the NAMES of the sent fields only: menu delete / reorder / categories / photo / sold-out, rewards, hourly reward, award-hour, waitlist switches, ...). A test walks every staff POST route in `server.js` and fails if a state-changing one writes no audit row. Money actions are written in the same transaction as the change. **Never stored: PINs, session / login keys, table tokens, the deposit-hook secret, the account number, SMS text** (pay settings only list which field names changed).

## 7. Realtime (SSE)

Endpoints (all `GET`, `text/event-stream`):

| Endpoint | Auth | Channel |
|---|---|---|
| `/api/t/<token>/events` | token | that table (+ this device's nick) |
| `/api/staff/events` | staff | staff |
| `/api/kitchen/events` | staff | kitchen |
| `/api/board/events` | none | board |
| `/api/wait/<id>/events?secret=` | secret | one waitlist entry |

Each connection starts with `retry: 3000`, then an immediate `state` event, then another `state` whenever the snapshot changes (changes are coalesced ~120 ms; identical snapshots are not re-sent). `: hb` comment every 20 s. Headers: `Cache-Control: no-cache, no-transform`, `X-Accel-Buffering: no`.

**`event: state`** — `data:` is the full JSON of the matching GET endpoint: guest = `GET /api/t/<token>`, staff = `GET /api/staff/state`, kitchen = `GET /api/kitchen`, board = `GET /api/board`, wait = `GET /api/wait/<id>`. Frontends can render purely from `state` events.

**Hint events** (small, immediate, optional; use for sounds/flash). The same data also arrives in the next `state`:

| Event | Channel | Data |
|---|---|---|
| `new_order` | staff | `{ id, table }` |
| `new_call` | staff | `{ id, table, type }` |
| `new_wait` | staff | `{ id }` |
| `new_deposit` | staff | `{ id, status }` — a bank deposit notice arrived and needs staff (`pending` or `unparsed`) |
| `deposit_matched` | staff | `{ id, status: "matched" }` — a notice was matched automatically and the order marked paid (the normal `state` follows) |
| `new_cooking` | kitchen | `{ id, table }` — an order just became `cooking` (also for staff-created orders with `accept`) |
| `order_status` | guest | `{ id, status }` |
| `cleared` | guest | `{ seat }` — staff cleared this table or moved it away; state already shows empty lists |

Use native `EventSource` (auto-reconnects with the `retry:` delay; cookies are sent). Pattern: open `EventSource`, on `error` also start a 5 s poll of the matching GET endpoint until `open` fires again. **Connection limits.** When a limit is exceeded the server **closes the oldest stream** (so `EventSource` silently reconnects after its `retry:` delay) instead of rejecting the new one: max 5 streams per device cookie, max **12 per guest table**, max **20** on `/api/board/events`, max **60** on wait streams. Guest + board + wait streams together are capped at **300** (503 `busy` beyond that); staff + kitchen streams have their own pool of 100 (oldest closed), so public traffic cannot take their slots. Cookie rules: a guest stream always has a device (the server mints `booth_d` on the first guest request); board/wait streams without a valid `booth_d` all share one bucket per channel type, so a cookie-less client can only hold 5 of them. **Slow readers:** state events are full snapshots, so a stream that cannot keep up simply receives the latest snapshot when it drains (intermediate states are skipped); a public stream with more than 64 KB of unsent data is dropped (it reconnects). Hint events may be skipped for a slow reader. Do not open more than one stream per page, and close it (`es.close()`) on page hide/unload.

## 8. Behaviour notes the frontends must respect

1. A cleared table's guests keep the same URL; after `cleared` the page should show an empty state ("새 손님을 환영해요") and reset local cart/nickname.
2. Guests identify only by cookie `booth_d`; if the user blocks cookies, nickname/plays/wait will not work. Show a hint on 4xx from `plays/start`.
3. Orders need staff acceptance: after 201 show "접수 대기"; staff moves it to `cooking`, then `served`. `paid` is independent (staff sets after confirming the transfer).
4. Item coupons (`type: "item"`) cannot be applied to orders (`coupon_not_discount`); the guest shows the 6-char code full screen for staff to redeem.
5. Sold-out/open-close/clear changes reach guests through the `state` event; cart lines for a sold-out item should be greyed out and the 409 `sold_out` response (`ids`) used to highlight them.
6. Display `message` strings from errors directly; they are Korean and end-user safe.
7. **Storage ceiling (new).** The database has a hard 256 MB size limit. When it is reached every write answers **503 `storage_full`** (reads keep working). Show the Korean `message`; staff must be told (they can export the CSV and reset). Not expected in normal use.
8. **Board caching (new).** `GET /api/board` (and the board `state`) may be up to 1.5 s old; any play result, nickname, award, stock change, clear, move or reset refreshes it immediately.
