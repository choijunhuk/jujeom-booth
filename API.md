# Booth server API contract

Single Node process: HTTP API + SSE + static files. Zero dependencies. This is the source of truth for frontend code. Config files (`menu.json`, `rewards.json`, `tables.json`) are read once at boot.

## 1. Base path, pages, static files

`BASE` = env `BASE_PATH` (default `""`, production `/booth`). nginx forwards the full path unchanged, so every route below lives under `BASE`.

**The frontend learns the base path from the server.** In every served `.html`, `.js` and `.css` file the literal token `__BASE__` is replaced with `BASE` (`""` or `/booth`, never a trailing slash). Write:

```html
<script src="__BASE__/static/base.js"></script>   <!-- public/base.js is exactly: window.BASE = "__BASE__"; -->
<script src="__BASE__/static/guest.js"></script>
<link rel="stylesheet" href="__BASE__/static/guest.css">
```

and call the API as `fetch(window.BASE + '/api/...')`. Never hard-code `/booth` or an absolute `/api`. Use relative-to-BASE URLs for `EventSource` too.

| Route (prefix with BASE) | Served file in `public/` | Notes |
|---|---|---|
| `/` (and `BASE` without slash) | built-in landing text | "scan the table QR" |
| `/t/<token>` | `guest.html` | 404 page for unknown token. Sets the `booth_d` device cookie. The token is the last path segment: `location.pathname.split('/').pop()` |
| `/wait` | `wait.html` | sets `booth_d` cookie |
| `/staff` | `staff.html` | page is public; it must show a PIN form and call login |
| `/staff/qr` | `qr.html` | page is public; data comes from `GET /api/staff/tables` (needs login) |
| `/kitchen` | `kitchen.html` | page is public; data needs the staff session |
| `/board` | `board.html` | public |
| `/sw.js` | `public/sw.js` | the booth service worker, **exactly** at `BASE/sw.js` (GET/HEAD). `Content-Type: text/javascript`, `Cache-Control: no-cache`, `Service-Worker-Allowed: <BASE>/` (so its scope is `BASE/`; `/` when BASE is empty), `__BASE__` substituted. 404 if the file is missing. Register it with `navigator.serviceWorker.register(window.BASE + '/sw.js', { scope: window.BASE + '/' })`. |
| `/static/<path>` | `public/<path>` | any file under `public/` (also `guest.html` etc.). Allowed extensions: html js mjs css json svg png jpg jpeg gif webp ico woff woff2 txt mp3 ogg wav webmanifest. Dotfiles and `..` -> 404. `Cache-Control: public, max-age=60` (HTML pages: `no-cache`). Put games at e.g. `public/games/pour.js` -> `__BASE__/static/games/pour.js` |

If a page file is missing the server answers a 404 page.

Security headers on everything: `X-Content-Type-Options: nosniff`, `Referrer-Policy: same-origin`, `X-Frame-Options: DENY`, CSP `default-src 'self'; script-src 'self'; worker-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data: blob:; media-src 'self' data: blob:; font-src 'self' data:; connect-src 'self'; object-src 'none'; base-uri 'self'; frame-ancestors 'none'; form-action 'self'`. So: **no inline `<script>` and no inline event handlers (`onclick=` etc.) — scripts must be separate `.js` files from `__BASE__/static/`** (put `window.BASE` in `public/base.js`, loaded first). Inline `<style>`/`style=` is still allowed. No external scripts/fonts/CDNs; images may be `data:`/`blob:`.

## 2. Conventions

- All API paths are `BASE/api/...`. All bodies/responses are JSON UTF-8. Times are epoch milliseconds. Money is integer won.
- **Every POST must send `Content-Type: application/json`** (even with body `{}`), otherwise 415. Body limit 16 KB (413). **One exception:** the photo upload `POST /api/staff/menu/items/<id>/photo` takes the raw image bytes (`image/jpeg|png|webp`, max 400 KB), see Menu photos.
- Error response (any non-2xx): `{ "error": "<code>", "message": "<Korean text safe to show>", ...extra }`. Switch on `error`, not on `message`.
- Common errors: 400 `bad_json`, 401 `unauthorized`, 403 `bad_origin`, 404 `not_found`/`no_table`, 413 `too_large`, 415 `unsupported_media_type`, 429 rate/limit codes, 500 `internal`, 503 `busy`.
- `table` is always the table number (1..N). Table numbers are also their ids.
- Cookies (both `HttpOnly`, `SameSite=Lax`, `Path=BASE||"/"`, `Secure` when `COOKIE_SECURE=1`): `booth_d` = anonymous device id, server-signed (`<id>.<signature>`; opaque to pages — never parse or forge it; an old or invalid value is silently replaced by a new one, so after an upgrade a browser just becomes a "new" device) (set automatically on guest pages/APIs, 3 days; used for nicknames, play limits, wait list), `booth_s` = staff session (default 72 h, env `SESSION_HOURS`), `booth_k` = staff trusted-device key (30 days, set on a successful login; see login). Names are prefixed so they cannot collide with the main site's cookies; if the browser sends duplicates of a name (different Paths), the server accepts any valid `booth_s` and the first well-formed `booth_d`. `fetch` on the same origin sends them automatically; no `credentials` option needed.
- Staff POSTs are rejected with 403 `bad_origin` when `Sec-Fetch-Site` is present and not `same-origin`/`none`, or (if that header is absent) when `Origin` is present and differs from `PUBLIC_ORIGIN`/`Host`. Normal same-origin `fetch` is fine.

## 3. Shared object shapes

**Menu item**: `{ id, name, price, cat, desc, soldOut, photo, stockLeft }` — **`stockLeft` (H10)**: for guests `null` unless a count is set AND it is 5 or less (show "N개 남음"); staff see the exact number (`null` = unlimited). `photo` is `null` or a path **relative to BASE** such as `/photos/12-ab12cd34.jpg` (use `<img src="` + `window.BASE` + `item.photo + `">`; the file name changes on every replace, so it can be cached forever). **Menu** (guest view): `{ categories: string[], items: MenuItem[] }` — items and categories come in the menu's display order; **hidden items never appear**, and a category with no visible item is omitted. The menu lives in the database and staff can edit it at any time (section 6, "Menu management"): re-render from every new `state`/`GET`, never cache prices for long. `price` is a multiple of 100 won. New item ids look like `m` + 10 hex chars; items seeded from `menu.json` keep their ids.
**Staff menu view** (inside staff `state` and in every menu-management response, as `menu`): same shape but includes hidden items, each item additionally has `hidden: boolean`, `sortOrder: number`, `categoryId: number`, `inUse: boolean` (it appears in some order, so it cannot be deleted), `stockAuto: boolean` (true while `soldOut` was set automatically by the stock counter reaching 0), and `stockLeft` is exact, and sets carry `components` (see H10b), and `categoryList: [ { id, name, sortOrder, itemCount } ]` lists every category including empty ones.

**Order**
```json
{ "id": 12, "table": 3, "seat": 1, "status": "pending|cooking|served|cancelled", "paid": false,
  "items": [ { "id": "tteokbokki", "name": "떡볶이", "qty": 2, "unitPrice": 8000, "service": false } ],
  "subtotal": 16000, "memberDiscount": 1600, "couponDiscount": 1000, "discount": 2600, "total": 13400,
  "member": true, "couponCode": "K3F9X2",
  "depositor": "홍길동", "paidBy": "auto",
  "createdBy": "guest|staff", "memberRule": null,
  "paidAmount": 13400, "paidMethod": "transfer|cash|other|null", "paidAt": 1731480000000,
  "balanceDue": 0, "overpaid": 0, "refundedAmount": 0, "refundDue": 0, "writtenOff": false,
  "note": "", "createdAt": 1731480000000, "updatedAt": 1731480000000, "cookingAt": null }
```
`depositor` is the name the guest typed for the bank transfer (`null` if none); `paidBy` is `null` (unpaid), `"staff"` (a staff member marked it, or assigned a deposit notice) or `"auto"` (confirmed automatically from a bank deposit notice). `couponCode` is `null` when none. `total = subtotal - memberDiscount - couponDiscount` (never below 0); `discount = memberDiscount + couponDiscount` is kept for older code. `member` is true when the order was placed by a verified COMS club member (the club id is never exposed). Amounts and item names/prices are frozen when the order is created: later menu edits, renames or price changes never alter an existing order (staff line edits, H2, keep them too for lines already on the order). Status flow: `pending` (waiting for staff accept) -> `cooking` -> `served`; `cancelled` is terminal.
**New in Release 2 (all derived from the money actually received):**
- `items[].service` (H3): a free "service" line (`unitPrice` 0, never part of `subtotal`).
- `createdBy` (H1): `"staff"` for orders made with `POST /api/staff/tables/<n>/orders`, otherwise `"guest"`. `memberRule`: the member-discount rule that was applied when the order was created (`{ mode, pct, amount, maxDiscount, minOrder }`) or `null` if no member discount applies (orders from before this field existed get a fixed rule equal to the discount they received, `legacy: 1`, so editing them keeps it); staff edits re-apply this stored rule, never today's settings.
- `paidAmount` (H5): money received for this order so far (partial payments add up); `paidMethod`: method of the latest payment; `paidAt`: when the order became fully paid (`null` while unpaid). **`paid` is true exactly when the money held (`paidAmount` minus refunds already paid back) covers `total`** (and the order is not free-and-unpaid). `balanceDue` = what is still missing (0 when `paid` or cancelled). `overpaid` = money held above `total` (0 for cancelled). **Release 3b:** the flag is recomputed by ONE routine after every payment, void, refund-done, edit, cancel, waive and restore; a cancelled / waived order keeps `paid: true` only while it still holds money (a void or a handed-back refund clears it), so it can never revive money after a restart.
- `refundDue` / `refundedAmount` (H6): money that must still be handed back / was already handed back. A cancelled order owes everything it received; a live order owes `paidAmount - total` when overpaid or after an edit lowered the total. `writtenOff` (H7): the order was left unpaid when staff force-cleared its table (미수금).
- `updatedAt` strictly increases on every change of the order (H15), so it can be sent back as `expectedUpdatedAt`.
- **Addendum J:** `test: boolean` — true for every order of the staff-only TEST table (table 0). **Feature I:** `kind: "food" | "cover"`. Staff view: `payments: [ { id, amount, shares, method, payer, at } ]` on EVERY order (the non-voided ledger; Σ amount = `paidAmount`; `id` is what `payments/<id>/void` takes). Cover orders (`kind: "cover"`, see "Headcount, cover charge, share payments") add `unitPrice`, `coverMode: "per_person"|"per_table"`, `waived` (status `cancelled` by a waiver), `shares: { total, paid, left } | null` (per-person only). In the GUEST snapshot a cover order's `payments` is reduced to `[ { shares, payer, at } ]` (no amounts, methods or ids) and food orders carry none.

**Coupon**
```json
{ "code": "K3F9X2", "rewardId": "d1000", "source": "score|hour|staff", "type": "discount|item",
  "amount": 1000, "item": null, "label": "안주 1,000원 할인", "status": "issued|used|void",
  "table": 3, "seat": 1, "orderId": null, "usedAt": null, "createdAt": 1731480000000 }
```
`amount` is set for `discount`, `item` (string) for `item` coupons. `source: "staff"` = made by hand (H11); `status: "void"` = cancelled by staff: it can no longer be applied or redeemed and is not shown to guests. Code alphabet has no `I O 0 1`; codes are upper-case, matching is case-insensitive.

**Game config** (`games` map in guest snapshot / `gameInfo` on board): `{ "pour": { "label", "maxScore", "minDurationMs" }, "cheers": {...} }`. Valid game ids are the keys of `games` in `rewards.json` (currently `pour`, `cheers`, `bug`, `typing`); nothing in the server assumes a fixed set, boards and rankings sum whatever games exist. `public/landing.html`, when present, replaces the built-in landing page at `BASE/` (`__BASE__` substituted, normal HTML headers); the built-in page is titled COMHERE.

## 4. Guest API (`BASE/api/t/<token>/...`)

Unknown token -> 404 `no_table`. Tokens are 16 chars of `[A-Za-z0-9_-]`. A guest only ever sees the table's **current seat** (round); staff "clear table" increments the seat, so old orders/coupons/calls disappear.

### `GET /api/t/<token>` — full snapshot (also the polling fallback; poll every ~5 s)
```json
{ "table": { "number": 3, "seat": 1 },
  "orderingOpen": true,
  "memberDiscountPct": 10,                   // older field = memberDiscount.pct
  "memberDiscount": { "enabled": true, "mode": "percent", "pct": 10, "amount": 1000, "minOrder": 0, "maxDiscount": 0, "stackWithCoupon": true },   // the staff-defined rule (display only); `enabled` = staff switch AND the feature is configured on the server. See GET .../member for whether THIS visitor is a member
  "menu": { "categories": [...], "items": [ MenuItem ] },   // hidden items are never included
  "orders": [ Order ],                       // current seat, newest first; cancelled orders: only the newest 5 are included
  "coupons": [ Coupon ],                     // current seat, oldest first
  "calls": [ { "id": 5, "type": "물", "createdAt": 0 } ],   // open staff calls
  "nick": "맥주왕",                          // this device's nickname for this seat, or null
  "rewards": [ { "id": "d1000", "game": "cheers", "label": "...", "type": "discount", "amount": 1000, "item": null,   // ACTIVE rewards only (staff can edit them any time; re-render on every state)
                 "threshold": 700, "soldOut": false, "got": false,
                 "seatIssued": 0, "seatLimit": 1, "limitSource": "people|fixed|override",     // K: coupons of this reward already issued to THIS seating / the limit that applies now
                 "deviceIssued": 0, "deviceLimit": 1,                                          // K: THIS device's coupons of this reward (never other devices' data); deviceLimit 0 = no limit (always 0 on the test table)
                 "seatCap": 4|null, "headcountTrusted": false, "headcountCounted": 1, "moreWithHeadcount": false, "moreWithStaffConfirm": false,   // K: seatCap = the reward's cap when limitSource is "people", else null. headcountTrusted = staff-set/confirmed or from the waitlist. headcountCounted = the effective headcount the per-seat limit uses (trust follows money, see below). moreWithHeadcount = paying more cover shares would raise the limit: limitSource "people", cap > headcountCounted, headcount not staff-trusted, a live per-person cover with UNPAID shares exists, nothing else (stock, device, table total) blocks. moreWithStaffConfirm = only staff confirming the headcount would raise it: "people", cap > 1, not trusted, no unpaid cover shares, nothing else blocks ("직원이 인원을 확인하면 한도가 늘어요")
                 "canEarn": true, "blockedBy"?: "seat_limit|device_limit|table_total_limit|stock_out" } ],  // K: blockedBy only when canEarn is false (the first reason, in that order)
  "couponSeat": { "couponsIssued": 2, "maxPerSeat": 0, "discountUses": 0, "maxDiscountUsesPerSeat": 0 },   // K: reward coupons issued to this seating (manual staff coupons excluded) / discount coupons applied to its orders; 0 = unlimited
  "games": { "pour": { "label": "...", "maxScore": 500, "minDurationMs": 8000 }, "cheers": {...} },
  "notice": { "text": "주문이 밀려요", "level": "info|warn" } | null,   // H9: staff banner
  "party": { "people": 4 | null, "askGuest": true, "canSet": false, "updatedAt": 0, "seatedAt": null },   // feature I1: this seating's headcount
  "cover": { Cover },             // feature I2/I3 (below)
  "callTypes": ["물", "수저", "치워주세요", "기타"],
  "pay": { "bank": "", "account": "", "holder": "", "tossEnabled": false, "kakaoPayUrl": "", "requireDepositor": false } }   // staff-editable payment settings (first boot: env PAY_BANK/PAY_ACCOUNT/PAY_HOLDER); empty strings if unset
```
`pay` is for the payment screen: show the account with a copy button. If `tossEnabled`, the page builds the Toss link itself from bank / account / the order total (the server generates no deep links); if `kakaoPayUrl` is not empty it is a staff-checked `https://qr.kakaopay.com/...` link to offer as a "카카오페이로 보내기" button. If `requireDepositor`, the order form must ask for the depositor name (the order is refused with 400 `depositor_required` otherwise).

### `POST /api/t/<token>/orders`
Body `{ "key": "<8-64 chars [A-Za-z0-9_-]>", "items": [ { "id": "tteokbokki", "qty": 2 } ], "couponCode": "K3F9X2"?, "note": "덜 맵게"?, "depositor": "홍길동"?, "expectedTotal": 15000? }`.
**New — `expectedTotal`** (optional integer, the total the guest saw on screen, after discounts): if it differs from the total the server computes now, the server answers **409 `price_changed`** and creates nothing. Payload: `{ error, message, expectedTotal, total, subtotal, memberDiscount, couponDiscount, items: [ { id, name, qty, unitPrice } ] }` with the fresh values. The page shows them, asks the guest to confirm, then resends with `expectedTotal` = the fresh `total`. **Nothing was created, so the client may reuse the same `key` or send a new one — both work.** Without `expectedTotal` the current price is charged as before. A non-integer value -> 400 `bad_expected_total`. Replays of an already-created key (`duplicate: true`) are answered before this check.
Generate `key` once per cart submission (`crypto.randomUUID()`), reuse it on retries. Prices sent by the client are ignored.
**New — `depositor`** (optional string; the name on the bank transfer): control/invisible characters are stripped, whitespace collapsed, 1..10 visible characters (no profanity filter); an empty string counts as absent. When staff turned on `requireDepositor` it is mandatory: 400 `depositor_required`. Invalid -> 400 `bad_depositor`. It is stored on the order and a replay of the same `key` returns the stored order unchanged. Staff use it (together with the amount) to match bank deposit notices.
- 201 `{ "order": Order, "duplicate": false, "memberDiscountSkipped": "limit"?, "couponIgnored": true? }` — **`couponIgnored: true`** (new) appears when the sent `couponCode` is valid but would discount 0 won (e.g. a free item, or nothing left after the member discount): the order is created without it, `order.couponCode` is `null` and the coupon stays unused. Tell the guest the coupon was not applied and is still available. — `memberDiscountSkipped: "limit"` appears only when the guest is a member who would have got a discount but already used it on the maximum number of orders (default 20 per club member, env `MEMBER_ORDER_MAX`); the order was created at full price. Show a short notice.
- 200 `{ "order": Order, "duplicate": true }` when this table **in its current seat** already used that key (the key is scoped to table+seat: after staff clears the table the same key creates a new order; returns the original; checked before everything else, even when ordering is closed).
- 400 `bad_key`, `bad_items` (empty / malformed), `too_many_lines` (>30 lines), `bad_qty` (not integer 1..20; `id` in payload), `dup_item` (same id twice), `unknown_item` (`ids`; also returned for hidden items), `bad_note` (>100 chars), `bad_coupon` (not found / not this table+seat), `coupon_not_discount`
- 409 `closed` (ordering switched off), `sold_out` (`ids`, `names`), `coupon_used`, `coupon_void` (H11), **`insufficient_stock`** (H10: `{ id, left, ids, names, items: [ { id, name, left } ] }` — the first short item and all of them; nothing was created, show "N개만 남았어요")
- 429 `too_many_pending` (10 orders waiting for acceptance at once)
- 429 `too_many_orders` (**new**: at most 40 orders per table per seat, cancelled ones included; resets when staff clears the table). Message tells the guest to ask staff.

A discount coupon is marked used together with the order; it returns to `issued` if the order is cancelled.

**Member discount.** Membership is decided by the server only: it forwards the visitor's club-site login cookie to the club backend (feature off unless env `COMS_ME_URL` is set). The request body is never trusted for membership (fields like `member` are ignored). The rule is set by staff (`POST /api/staff/member-discount`, below): `enabled`, `mode` (`percent` | `fixed`), `pct`, `amount`, `minOrder`, `maxDiscount`, `includeAssociate`, `perMemberLimit`, `stackWithCoupon`. For an eligible member the order's `memberDiscount` is computed as: 0 if `subtotal < minOrder`; otherwise percent mode `floor(subtotal * pct / 100 / 100) * 100` (rounded DOWN to 100 won; 8,500 won at 10% = 800, at 15% = 1,200; 900 won at 10% = 0) or fixed mode `amount`; then `min(discount, maxDiscount if maxDiscount > 0, subtotal)`. It is applied to the subtotal **first**; a selected coupon is then applied to what is left; the total never goes below 0. Eligible = verified club member AND staff switch `enabled` AND (`includeAssociate` OR the club role is not `ASSOCIATE`). When `stackWithCoupon` is false and the guest selected a coupon, the coupon wins: the member discount is 0 and the 201 response carries `memberDiscountSkipped: "coupon"`. When the member already used the discount on `perMemberLimit` non-cancelled orders the order is created at full member-less price with `memberDiscountSkipped: "limit"` (the limit is only known at order time). Cancelling an order restores its coupon and frees its member-discount slot. `expectedTotal` / 409 `price_changed` protects the guest against any mismatch between the shown and the computed total.

### `GET /api/t/<token>/member`
-> `{ "enabled": boolean, "member": boolean, "mode": "percent"|"fixed", "pct": number, "amount": number, "minOrder": number, "maxDiscount": number, "stackWithCoupon": boolean }`. `enabled` is false when the feature is off — either not configured on the server or switched off by staff (no outbound request is made then). `member` is true when the browser's club login is valid right now (cached 60 s) AND the visitor is eligible under the staff rule (the `ASSOCIATE` role is excluded when staff set `includeAssociate: false`; the per-member limit is NOT considered here, it is reported at order time via `memberDiscountSkipped`). The other fields are the rule, so the page can display and pre-compute the discount (subtotal >= `minOrder`; percent: `floor(subtotal*pct/10000)*100`, fixed: `amount`; then cap by `maxDiscount` when > 0 and by the subtotal; if `stackWithCoupon` is false a selected coupon replaces it). Only these fields are returned: never a name, id or role. The actual discount is always decided again at order time. Cheap to call; do not poll faster than every ~30 s. Not logged in / expired / banned / club server down all simply give `member: false`.
**Rules the page must know (new):** (1) a lookup needs a `booth_d` device cookie that already existed when the request arrived — the first request of a brand-new browser (which only mints the cookie) answers `member: false`; load the guest snapshot first (every guest page does), then call `/member`, and call it again once the first answer was `false` while a club login cookie is present only if you want a retry. The same applies to the member discount at order time. (2) Each device gets at most 6 uncached lookups per minute; beyond that it is simply treated as a non-member until the minute passes. (3) Only definitive answers are cached for 60 s: a valid member, or the club saying 401/403. Timeouts, 5xx, 429, redirects and unreadable answers are never cached (the next call asks again). (4) Any logged-in club account counts as a member; the `ASSOCIATE` role only if staff left `includeAssociate` on (default on). (5) A guest who logs out of the club site keeps the discount for up to 60 s (cache).

### `POST /api/t/<token>/orders/<orderId>/cancel` — body `{}`
Only own-table, current-seat, `pending` orders with NO money received (a partly paid order is refused too). 200 `{ order }`. 404 `no_order`, 409 `not_cancellable`.

### `POST /api/t/<token>/orders/<orderId>/depositor` — body `{ "depositor": "홍길동" }`
Lets the guest fix the depositor name of an own, current-seat order while it is unpaid. 200 `{ order }`. 400 `bad_depositor`, 404 `no_order` (also another table's order), 409 `already_paid`, 409 `order_cancelled`. (A deposit notice that already arrived with the old name stays pending for staff; it is not re-matched automatically.)

### `POST /api/t/<token>/nick` — body `{ "nick": "맥주왕" }`
Control, zero-width, bidi, Hangul-filler (U+3164, U+115F, U+1160, U+FFA0), braille-blank and lone-surrogate characters are stripped, whitespace collapsed; at least one visible character (checked after NFKC) and 1..10 characters are required; profanity blocklist. The stored nick keeps the typed form. 200 `{ "nick": "<cleaned>" }`. 400 `bad_nick`. Per device per seat. Shown on the board. **New errors:** 400 `no_device` (the request did not carry an existing valid `booth_d` cookie — a cookie minted by this very response does not count; load `GET /api/t/<token>` first, which every guest page does; after a `no_device` just retry), 429 `too_many_nicks` (30 nicknames per table seat; existing devices can still rename).

### `POST /api/t/<token>/plays/start` — body `{ "game": "pour" }`
200 `{ "playId": 41, "game": "pour", "startedAt": 0, "maxScore": 500 }`. Server records the start time. 400 `bad_game`; 429 `rate_limited` (`retryAfterMs`; max 1 start per 3 s per device **and, new, 1 start per 1 s per table seat** — friends at the same table starting together may need to retry after `retryAfterMs`), `device_limit` (200 plays per device total), `seat_limit` (**new**: 300 plays per table seat in total), `too_many_open` (**new**: 20 started-but-unfinished plays (younger than 10 min) per seat).

### `POST /api/t/<token>/plays/finish` — body `{ "playId": 41, "score": 430 }`
`score` must be an integer. Accepted once per play.
200:
```json
{ "score": 430,
  "coupons": [ Coupon ],                       // newly issued by this finish
  "rewards": [ { "rewardId": "drink", "id": "drink", "label": "음료 1잔", "earned": true,
                 "reason"?: "low_score|seat_limit|device_limit|table_total_limit|stock_out",   // K: machine-readable, only when earned is false
                 "result": "issued|low_score|already_got|device_limit|table_total_limit|sold_out",   // older field, kept (seat_limit -> "already_got", stock_out -> "sold_out")
                 "coupon": Coupon /* only when issued */ } ] }
```
`rewards` lists every reward of this game so the UI can say "재고 소진" / "점수 부족" / "이미 받음".
Errors: 400 `bad_play`, 400 `bad_score` (non-integer, or outside `0..maxScore`), 400 `too_fast` (shorter than the game's `minDurationMs`), 400 `too_slow` (>10 min), 404 `no_play` (unknown play / other device / other table / seat was cleared or the table was moved away), 409 `already_finished`. A play rejected for `bad_score` (range) / `too_fast` / `too_slow` is burned: it cannot be resubmitted (further finish -> 409). Malformed values (`bad_play`, non-integer score) do not burn it. Games must therefore run at least `minDurationMs` of real time (default `pour` 8000 ms, `cheers` 10000 ms) and never exceed `maxScore` (`pour` 500 = 5 glasses x 100, `cheers` 1000 = 10 taps x 100).
Coupon rule: score >= reward `threshold`, stock left, and this table+seat has not already received that reward.

### Order actions
**Dry-run preview (`dryRun: true`):** `POST /api/staff/orders/<id>/items`, `/service`, `/paid` and `POST /api/staff/tables/<n>/orders` accept `"dryRun": true` (literal true only). The server runs the real code in a transaction that is rolled back and answers `{ "dryRun": true, "order": Order }` (for order creation also `duplicate`) — exactly what the real call would return: new lines, `subtotal`, `memberDiscount`, `couponDiscount`, `total`, `balanceDue` / `refundDue` / `overpaid`, `paid`. The same validation applies, so problems come back as the real errors (e.g. 409 `insufficient_stock`, `sold_out`, `stale`, 400 `no_lines`). **Nothing is written:** no audit row, no stock change, no `updatedAt` bump, no SSE (state is byte-identical before and after). Times in the preview (`updatedAt`, `paidAt`, `createdAt`) are not those of a later real call.
Every action below re-reads the order inside its transaction. **H15 — `expectedUpdatedAt` (optional integer, the order's `updatedAt` the client rendered):** when given and different from the current value nothing is applied and the server answers **409 `stale`** `{ error, message, order: <current Order> }` — show the fresh order and let the staff member retry. Omitted = no check (old behaviour). A non-integer -> 400 `bad_expected`. Accepted by `status`, `paid`, `items`, `service`, `move` and `refunds/<id>/done` (checked against the refund's order).
- `POST /api/staff/orders/<id>/status` body `{ "status": "pending|cooking|served|cancelled", "expectedUpdatedAt"? }` -> `{ order }`. Any change between the first three is allowed (undo a mis-tap); accept = `cooking`, done = `served`. `cancelled` restores an applied discount coupon and the stock (H10) and is terminal (409 `order_cancelled` afterwards); **money already received on a cancelled order becomes a refund entry (H6)**. 400 `bad_status`, 404 `no_order`, 409 `stale`.
- `POST /api/staff/orders/<id>/paid` body `{ "paid": true, "method"?: "transfer|cash|other", "amount"?: won, "payBalance"?: true, "expectedUpdatedAt"? }` -> `{ order }` (**H5**; **3e: `payBalance: true`** = "남은 금액 전부 받기": records EXACTLY the current balance, `paid` may be left out, cannot be combined with `amount` / `shares` / `paid: false` -> 400 `bad_pay_balance`; on a per-person cover order a balance that is a whole number of shares is booked as that many shares, any other remainder (e.g. 500 of a 3,000 share) as a plain money payment with `shares: null`, never a fraction of a share; an already fully paid order answers 409 `stale`). `paid: true` ADDS a payment of `amount` (default: the remaining balance = `balanceDue`, i.e. `total − (paidAmount − refundedAmount)`; so after a refund was paid out and the order grew again, a bare `{ paid: true }` settles it in one call; `method` default `transfer`): the order becomes `paid: true` once the money held covers `total`; less leaves it unpaid with a `balanceDue`; more records `overpaid` and opens a refund entry for the excess. `paidBy` is `"staff"`. A second `paid: true` WITHOUT `amount` on an already fully paid order is refused with **409 `stale`** (a double tap from another phone must never double-apply); with an explicit `amount` it adds the money. `paid: false` removes every payment of the order (clears `paidAmount`/`paidMethod`/`paidAt`, deletes open refund entries, hands EVERY deposit notice linked to the order back to `pending`); refused with **409 `has_refunds`** once any refund of the order was paid back. 400 `bad_paid`, `bad_method`, `bad_amount` (integer 0..10,000,000; 0 only for free orders), 409 `order_cancelled`, 409 `stale`.
- **`POST /api/staff/tables/<n>/orders` (H1)** body `{ "key": "<8-64 chars>", "items": [ { "id", "qty" } ], "note"?, "depositor"?, "allowHidden"?: true, "accept"?: true }` -> 201 `{ order, duplicate: false }` / 200 `{ order, duplicate: true }`. Staff create an order for a table's current seat (phone / paper orders). Same validation as guests (`bad_key`, `bad_items`, `bad_qty`, `dup_item`, `too_many_lines`, `unknown_item`, `sold_out`, `insufficient_stock`, `bad_note`, `bad_depositor`), plus: **no member discount and no coupon** (`couponCode` -> 400 `coupon_not_allowed`), **allowed while ordering is closed**, never needs `depositor`, `createdBy: "staff"`, the order cap is **80** per seat (guests: 40) -> 429 `too_many_orders`. `accept: true` = staff accepts it at once: the order is created already `cooking` (it appears in the kitchen, kitchen SSE `new_cooking`, and its guests get `order_status`); without it the order is `pending` and goes through the normal accept step. **Response:** `{ "order": Order, "duplicate": false }` with HTTP 201 for a new order, `{ order, duplicate: true }` with 200 for a replayed `key`. The order has `createdBy: "staff"` and no member discount. Idempotent by `key` per table+seat. Hidden items are refused (`unknown_item`) unless `allowHidden: true` (then they are not sold-out checked either). 404 `no_table`.
- **`POST /api/staff/orders/<id>/items` (H2)** body `{ "items": [ { "id", "qty": 0..20, "service"?: true } ], "expectedUpdatedAt"? }` -> `{ order }`. REPLACES the order's normal lines with the listed ones (a line not listed is removed; `qty: 0` also removes it; at least one normal line must remain: 400 `no_lines`, cancel the order instead). **Lines already on the order keep their original name and unit price; only lines added now use the current menu price.** Free service lines are kept unless listed. The member discount is recomputed from the rule stored on the order (`memberRule`), a coupon on the order becomes `min(coupon amount, remaining)`, the total never goes below 0. Payments are kept: if the order was paid and the new total is lower it stays `paid` with `overpaid`/`refundDue` and an open refund entry; if higher it becomes `paid: false` with a `balanceDue`. Stock follows the change in quantity (reducing gives stock back, adding takes it: 409 `insufficient_stock`). Errors: 400 `bad_items`, `bad_qty`, `dup_item`, `unknown_item`, `no_lines`; 404 `no_order`; 409 `order_cancelled`, `sold_out` (only when the quantity of a sold-out item grows), `insufficient_stock`, `stale`. Totals do not change. It uses the item's stock like a normal line, shows in the kitchen (`items[].service`) and in sales (`byItem[].serviceQty`). 400 `bad_qty` / `bad_items`, `unknown_item`; 409 `sold_out`, `insufficient_stock`, `order_cancelled`, `stale`; 404 `no_order`.

- **`POST /api/staff/refunds/<id>/done` (H6)** body `{ "amount": integer (REQUIRED), "method"?: "transfer|cash|other" (default cash; recorded and summed in `byMethod.refunded`), "note"?: 1..60 chars, "expectedUpdatedAt"? }` -> `{ ok, refund }`: staff handed the money back. **`amount` must equal the entry's CURRENT amount** (what the staff member saw and handed over); if a concurrent edit changed it: **409 `refund_changed`** `{ refund: <current entry> }` and nothing is recorded. 400 `bad_amount` (missing / not a positive integer), `bad_method`, `bad_note`; 404 `no_refund`; 409 `refund_done`, `stale`.

### Menu management (new)
The menu is stored in the database. On the very first boot (empty menu tables, also when upgrading an older database) it is seeded once from `menu.json` and a `menu_seeded` flag is stored; after that the database is the source of truth and `menu.json` is never read again — not even if staff later delete every item and category, and not after a reset. All endpoints below need the staff session, same-origin and JSON; success responses are `{ ok: true, menu: <staff menu view>, item?: <staff item>, category?: { id, name } }` (re-render from `menu`). Every edit is pushed over SSE to guests and staff.
Rules: item `name` 1..30 characters after control/invisible-character stripping (zero-width, bidi, Hangul fillers) and trimming, must contain at least one visible character (else 400 `bad_name`), stored exactly as typed (trimmed, inner whitespace collapsed), and unique among all items **on a normalised key** (NFKC, collapsed whitespace, case-insensitive: "Beer", "beer" and fullwidth "Ｂｅｅｒ" are the same name -> 409 `name_taken`; same rule for category names, and an item sent with `category: "dessert"` goes into the existing "Dessert" category); `price` integer 0..1,000,000 and a **multiple of 100**; `desc` 0..60 characters; category name 1..12 characters, unique; at most **100 items** and **12 categories**. Hidden items are not shown to guests and cannot be ordered (400 `unknown_item`, same as a nonexistent id); sold-out items are shown greyed and cannot be ordered (409 `sold_out`).
- `POST /api/staff/menu/items` body `{ "name", "price", "category": "안주", "desc"?: "", "hidden"?: false }` (**new `hidden`**: create an item already hidden so guests never see it; non-boolean -> 400 `bad_hidden`) -> `{ ok, item, menu }`. `category` is a category NAME; it is created if missing. 400 `bad_name` / `bad_price` / `bad_desc` / `bad_category`, 409 `name_taken` / `too_many_items` / `too_many_categories`.
- **H10 — stock counter:** `POST /api/staff/menu/items` and `POST /api/staff/menu/items/<id>` also accept `"stockLeft": integer 0..9999 | null` (`null` = unlimited; others -> 400 `bad_stock_left`). Setting `stockLeft: 0` by hand is an automatic sold-out too, raising it (or `null`) lifts it. `reset` / day close keep the numbers and clear the sold-out flags, except that an item whose count is 0 stays (automatically) sold out until staff raise the count.
- **H10b — set menus (components):** `POST /api/staff/menu/items` and `POST /api/staff/menu/items/<id>` also accept `"components": [ { "id": <item id>, "qty": 1..10 } ] | null` (`null` or `[]` clears; at most 6 entries; 400 `bad_components` with a Korean message for: not a list, bad/duplicate entry, unknown id, the item itself, a component that is itself a set, or an item that is already used as a component). `menu.json` items may carry the same `components` (validated at seed time; an invalid file seeds nothing). A set item (the STAFF menu view carries `components: [ { id, qty, name } ]` and `blockedBy: [component names]` (the components that are sold out or too low; non-empty means the set is sold out because of them and staff cannot toggle it by hand); guests never get these keys; both are absent for normal items; every staff item also has `ownStockLeft`, the raw counter of the item itself, while a set's `stockLeft` is the computed minimum) consumes `qty x n` of every component's stock counter whenever it is ordered (orders, staff edits, service lines) and gives it back on cancel/reduce; its own `stockLeft`, if set, applies as well. The order pre-check adds up demand per stock item over all lines and components (라면 x2 + 라면세트 x1 = 3 라면); a shortage is `409 insufficient_stock` (same payload shape; `ids`/`names`/`items` name the ordered lines, the message names the component; each line's `left` is its share when the remaining stock is handed out line by line in cart order (라면 2 left, cart 라면 x2 + 라면세트 x2 -> 라면 2, 세트 0), so clamping every line to its `left` gives an orderable cart). A set is `soldOut: true` (and ordering it is `409 sold_out`) while any component is sold out (by hand or automatically) or has fewer left than one set needs. A set's `stockLeft` = the smallest of its own counter and `floor(component.stockLeft / qty)` over the limited components (`null` if all unlimited); guests still only see it when 5 or less. Deleting an item that is a component of a set is `409 in_use`. The test table never consumes stock. Changing a set's components (any difference, including adding or clearing them) is refused with `409 set_in_use` while any real-table order that is not cancelled contains that item (normal or service line); test-table orders do not count. Served orders count too: cancel those orders or close the day first, so a cancel can never return stock that was never taken. (Data from before this rule is not reconciled: an order placed before a set got its components still gives them back when cancelled.)

### Reward management
Rewards live in the database (seeded once from `rewards.json`, which is never read again for rewards afterwards; an invalid file logs `rewards.json is invalid: …` and starts with no rewards). Games (`pour`, `cheers`) with `maxScore` / `minDurationMs` stay read-only constants. At most 12 rewards.
**Reward**: `{ id, label, game: "pour"|"cheers", threshold, type: "discount"|"item", amount: won|null, item: string|null, stock, issued, remaining, used, active }` — `stock` = configured total, `issued` = coupons handed out, `remaining = stock - issued`, `used` = redeemed or applied coupons. **K:** plus `perSeat: { mode: "people"|"fixed", count: 1..20, cap: 1..20 }` and `perDevice: 0..20`. New ids look like `r` + 8 hex; seeded ones keep their ids.
Rules: `label` 1..20 visible characters; `game` one of the games; `threshold` integer 0..that game's `maxScore`; `type` `discount` needs `amount` (integer, multiple of 100, 100..100000), for `item` any `amount` is ignored (stored null; the coupon's `item` text is the label); `stock` integer 0..10000; `active` boolean (default true on create). **K limits:** `perSeat` (default `{ mode: "people", count: 1, cap: 4 }`; on update a partial object merges onto the current value, unknown keys / bad values -> 400 `bad_per_seat`) and `perDevice` (integer 0..20, default 1, 0 = no device limit; else 400 `bad_per_device`).
- `GET /api/staff/rewards` -> `{ rewards: [Reward], hourly, games }` (the same data is in staff `state`).
- `POST /api/staff/rewards` body `{ label, game, threshold, type, amount?, stock, active? }` -> `{ ok, reward, rewards }`. 400 `bad_label` / `bad_game` / `bad_threshold` / `bad_type` / `bad_amount` / `bad_stock` / `bad_active`, 409 `too_many_rewards`.
- `POST /api/staff/rewards/<id>` body: any of `label, game, threshold, type, amount, stock, active, perSeat, perDevice` -> `{ ok, reward, rewards }`. 400 `nothing_to_update` and the codes above, 400 `stock_below_issued` (`issued` in payload; stock may equal issued, never be lower), 404 `no_reward`. Changing `type` to `discount` needs an `amount`. **Edits only affect coupons issued afterwards:** every coupon stores its own label, type and amount at issue time, and applying/redeeming uses those stored values.
- `POST /api/staff/rewards/<id>/delete` body `{}` -> `{ ok, rewards }`. 409 `in_use` if anything was ever issued (deactivate instead); 404 `no_reward`.
- `POST /api/staff/rewards/<id>/stock` (older endpoint, still works) body `{ "stock": n }` -> `{ ok }`; same rules.
- **Inactive** (`active: false`) rewards are hidden from guests and the board and are never issued; coupons already issued stay valid. Several rewards may target the same game: one play can earn each of them. **Release K — coupon limits.** One transaction decides every reward of a finished play, from CURRENT values, in this order (the first failing check is the `reason`): (1) `seat_limit`: coupons of this reward already issued to this seating (table + seat, any status) `>=` the per-seat limit, where the limit is the staff override of the seating if set (`limitSource: "override"`), else for `perSeat.mode: "people"` `min(effective headcount, perSeat.cap)` (`"people"`). **Trust follows money:** the effective headcount (`headcountCounted`) is the seat's `people` when STAFF set or confirmed it (`party.setBy: "staff"`, including re-entering the same number) or it came from the WAITLIST (`"waitlist"`, `headcountTrusted: true`); otherwise (guest-entered) it is `min(people, shares really PAID on a live per-person cover order)` (`shares.paid`, counted from the money held), never below 1; no cover, per-table cover, waived cover, or nothing paid = 1. So a guest typing 30 people gets 1 per reward until cover shares are paid (2 paid = 2, and so on), never more than `cap`. It is evaluated at every finish, so shares paid later raise it then; a void or refund that lowers the paid shares never revokes issued coupons, it only blocks further ones, else `perSeat.count` (`"fixed"`; the headcount does not matter); (2) `device_limit` (a speed bump, NOT a security bound: a fresh browser session mints a new signed device id): `perDevice > 0` and the signed `booth_d` device already got `perDevice` coupons of this reward on any real table since the last reset / day close (no valid device = no coupon); (3) `table_total_limit`: `couponLimits.maxPerSeat > 0` and the seating already got that many reward coupons of any kind (hourly award included, manual staff coupons NOT); (4) `stock_out`. A refused reward never touches stock. Each issued coupon records the per-seat limit and its source that applied (`Coupon.limit`, `Coupon.limitSource`; null for manual / hourly / older coupons). Lowering `people`, the cap or an override never revokes issued coupons; it only blocks further issues. The TEST table (0) keeps unlimited stock and no device / table-total limits (the per-seat limit still applies), and its coupons never count toward real device limits. **Move / merge:** coupons travel with the table move, so after a merge the destination seating counts the union of both seatings' coupons and uses the DESTINATION's headcount (the merged sum, still capped) and override. **Migration (boot; atomic: the column defaults carry the data, there is no follow-up UPDATE to lose, so a kill in the middle cannot leave old rewards on the new default):** rewards that existed before the upgrade (including those seeded from an old `reward_stock` database) get `perSeat { mode: "fixed", count: 1, cap: 4 }` and `perDevice 1` (exactly today's one coupon per seating whatever the headcount); only rewards created afterwards default to `{ people, 1, 4 }`; existing coupons have no device id and never block anyone; `couponLimits` default `{0, 0}`.
- **`POST /api/staff/coupon-limits`** body any of `{ "maxPerSeat": 0 | 1..50, "maxDiscountUsesPerSeat": 0 | 1..50 }` (0 = unlimited) -> `{ ok, couponLimits }`; `GET /api/staff/coupon-limits` -> `{ couponLimits }`; also `state.couponLimits`. 400 `bad_coupon_limit`, 400 `nothing_to_update`. Audited (`coupon_limits`, Korean summary). `maxDiscountUsesPerSeat` counts non-cancelled orders of the seating that carry a discount coupon: an order with one beyond the limit is refused with **409 `coupon_limit` `{ max, used }`** and nothing is consumed; cancelling an order frees its use. Not applied on the test table (its `couponSeat.maxDiscountUsesPerSeat` is 0). **Any** discount coupon applied to an order counts as a use, manual staff coupons included (they are excluded only from `maxPerSeat`). **Counter redeem:** `POST /api/staff/coupons/redeem` of a DISCOUNT coupon counts as a use of the coupon's own seating (the same rule, 409 `coupon_limit { max, used }` at the limit, nothing consumed); `item` coupons are unaffected. Redeeming a TEST-table coupon answers `coupon.test: true` and writes an audit row that says 테스트 (no real item or discount must be handed out); it never touches real `used` counts. **Order move:** `POST /api/staff/orders/<id>/move` of an order that carries an applied coupon into a seating already at the limit -> 409 `coupon_limit { max, used }`, nothing changes. Moving an order frees a use at the source seating and occupies one at the destination (both visible in `tables[].discountUses`). **Move / merge and the headcount:** a merged seating's headcount is trusted (`setBy: "staff"`) only when BOTH seatings' headcounts were trusted; if either was guest-entered the result is `setBy: "guest"` (untrusted) until staff confirm it; a move into an empty seat keeps the source's `setBy`. A whole-table move / merge is never refused: the merged seating's `discountUses` can exceed the limit (both seatings' orders are counted), and further coupon uses there are then refused until it falls below it.
- **`POST /api/staff/tables/<n>/coupon-limit`** body `{ "perSeat": 0..20 | null }` -> `{ ok, table, seat, couponLimitOverride }`: replaces the per-seat limit of EVERY reward for that table's CURRENT seating only (`0` = no reward coupons for this seating, `null` clears). A new seating (after clear) starts without it, undo-clear restores the previous seating's, a table move keeps the destination's. 400 `bad_per_seat`, 404 unknown table. Audited (`coupon_limit_override`). Exposed as `tables[].couponLimitOverride` (number | null) in staff state. The test table (`state.testTable`) carries `couponLimitOverride`, `couponsIssued` and `discountUses` too. Changing a reward's `perSeat` / `perDevice` also writes an audit row `reward_limits` (Korean summary). **Staff tables:** every `tables[]` entry and `state.testTable` carry `headcountTrusted: boolean`, `headcountCounted: number` and `couponLimits: [{ rewardId, limit, limitSource: "people"|"fixed"|"override" }]` (active rewards), computed by the same functions the issuing code uses; the staff UI must show these and never compute limits itself. A waived per-person cover with a guest-entered headcount gives `headcountTrusted: false` and `headcountCounted: 1`.
- **Coupon bound (what staff can promise).** Let L(r, s) be the per-seat limit of reward r at seating s when it is issued (override, else `fixed` count, else `min(headcountCounted, cap)`; at most 20). (1) **Per seating and reward:** issued <= L(r, s), always; lowering any setting never revokes but blocks more. (2) **Per seating, all rewards:** <= `maxPerSeat` when it is set (the hourly award counts toward it but is never blocked by it), else <= the sum of L over the active rewards. (3) **Per reward overall:** <= min(`stock`, sum of L(r, s) over all seatings of the day); seatings are created only by staff (clear, table move source, reset), never by a guest. (4) **What a guest can raise by themselves:** nothing by typing a headcount (it counts as 1 until staff confirm it); only by really paying cover shares (per-person cover), up to the shares paid and never above `cap`. Rewards that existed before the upgrade are `fixed` 1 (exactly one per seating). (5) `perDevice` is NOT a bound against a determined guest (a new browser session is a new device); it only slows casual repeats. The real bounds are 1-3 above and the stock. Careless settings widen the bound: `fixed` count / `cap` 20, an override of 20, `maxPerSeat` 0, a huge `stock`.
- Reward edits are pushed live (guest, board and staff SSE).
- **Hourly ranking reward:** `POST /api/staff/hourly-reward` body any of `{ "label": 1..20 chars, "type": "item"|"discount", "amount": 100..100000 step 100 (required when type is discount), "enabled": boolean }` -> `{ ok, hourly: { enabled, label, type, amount, item } }`; 400 `nothing_to_update` / `bad_label` / `bad_type` / `bad_amount` / `bad_enabled`. `POST /api/staff/award-hour` issues a coupon of that type/amount/label and now answers **409 `hourly_disabled`** while `enabled` is false. The same object is `hourly` in staff state and the board snapshot.

### Deposit notices (semi-automatic payment confirmation)
A phone (SMS forwarder / automation app) sends every bank deposit text to the booth; matching an order is conservative.

**Auto-confirm is OFF by default (fresh installs, and forced off once on every existing database).** Why: the name printed in a bank SMS is typed by the *sender*, so every character of the notice is attacker-controlled, and a name + amount match can be guessed or gamed. With auto-confirm off the hook still receives and parses every notice; staff see each one as `pending` with `reasons` (for a perfect notice: `["auto_off"]`) and the candidate orders, and confirm with one tap (`assign`). Staff may switch auto-confirm on (`autoConfirm: true`), and even then it only fires for amounts up to `autoConfirmMaxAmount` (default **30,000** won) and only when every rule below holds; anything doubtful stays manual.
- **Webhook URL staff copy:** `GET /api/staff/deposit-hook` -> `{ secret, path, url, header, headerUrl, lastNoticeAt, lastMatchedAt }` (**`lastNoticeAt`** = newest received notice of any status or `null`, **`lastMatchedAt`** = newest match or `null`; the same two fields are in staff `state.deposit` and `GET /api/staff/deposits`, so the UI can tell whether the phone still forwards) where `url` = `<PUBLIC_ORIGIN><BASE>/api/deposit-hook/<64 hex secret>`, e.g. `https://coms.kw.ac.kr/booth/api/deposit-hook/3f9c…(64 hex)…a1`. `POST /api/staff/deposit-hook/rotate` body `{}` -> `{ ok, secret, path, url, header, headerUrl }` makes a new secret ("재발급"); the old URL stops working at once. The secret is generated once and kept across restarts and resets; it is never sent to guests.
- **Secret in a header instead of the URL (new):** `POST <BASE>/api/deposit-hook` with the header `X-Booth-Hook: <secret>` (`headerUrl` = `<PUBLIC_ORIGIN><BASE>/api/deposit-hook`, `header` = `X-Booth-Hook`) behaves exactly like the path form, so the secret need not appear in any URL / access log. Both forms stay valid; rotation invalidates both.
- **The hook itself:** `POST <BASE>/api/deposit-hook/<secret>`, no session, no Origin / same-origin check (the secret in the path is the credential, compared in constant time). Body: JSON `{ "text": "..." }` (`Content-Type: application/json`) or the raw text (`Content-Type: text/plain`), max 2 KB (413; other types 415; bad JSON 400 `bad_json`; no `text` string 400 `bad_body`). A wrong secret answers `404 { error: "not_found" }` after a fixed 300 ms delay; wrong-secret attempts have their own budget (20 per minute and at most 20 delayed at a time, the rest answer immediately) and never consume the real forwarder's 60 per minute. Requests with the right secret count toward the 60 per minute only once they are well-formed. At most 60 accepted notices per minute server-wide (429 `rate_limited`; also 429 `queue_full` when 1500 notices already wait for staff — `hookRateLimited` is set for both). Answer: `{ ok: true, status, id? }` with `status` one of `matched`, `pending`, `review`, `unparsed`, `duplicate` (an identical normalised text less than 5 seconds after the previous one = a forwarder retry: dropped, nothing stored — the only silent drop) or `ignored` (stored for staff but never matchable, see Parsing). Stored notices also return their `id`. It never reveals which order matched.
- **Parsing (security note: the sender controls the name printed in the SMS, so every character is untrusted).** A text without `입금` is `ignored` (withdrawals, ads). A text that contains `입금` AND a reversal/correction/withdrawal word (`출금` — but not inside `입출금` such as KakaoBank's 입출금통장 —, `취소`, `정정`, `오류`, `반환`, `실패`, or `입금` directly followed by `계좌`/`취소`/`은행`/`예정`/`한도`), or is longer than 300 characters (`text_too_long`), gets status **`review`**: counted in the pending badge, assignable only with `force: true`, never automatic (so a real deposit from 정정훈 is not lost). Otherwise the text is normalised (NFKC: full-width digits become ASCII; U+2028/U+2029 become spaces), masked account fragments, dates and times are removed as whole tokens, and **a balance is removed only when `잔액 <number>` STARTS a line** (a sender-typed "잔액" in the middle of a line can never hide the real amount); the remaining amount-shaped numbers are counted. **A notice is `autoEligible` only if exactly ONE amount-shaped number remains (100..10,000,000), exactly ONE name token remains that is 2..10 Hangul/Latin letters (no digits, no `원`, `,`, `.`), and the name and the amount are on different lines or separated by the literal word `입금`** (otherwise `amount_adjacent_to_name`: single-line SMS such as `홍길동님이 16,000원을 입금했습니다` are display-only). Bank names and template words (스마트폰뱅킹, 입출금통장, 통장, From, 모바일 …) are skipped. Not eligible notices carry `reasons` (`multiple_amounts`, `no_amount`, `amount_range`, `no_name`, `name_has_digit`, `name_shape`, `several_names`, `amount_adjacent_to_name`, `text_too_long`); a best-guess amount is still stored for display. **Release 3e — `amountGuessed` (exact definition):** true ONLY when the AMOUNT is uncertain, i.e. the parse reasons contain one of `ignore_word`, `multiple_amounts`, `no_amount`, `amount_range`, `amount_adjacent_to_name`, `text_too_long` (then the stored amount is a guess: show "추정 금액", staff must force + type the amount, see assign). The NAME reasons (`no_name`, `name_has_digit`, `name_shape`, `several_names`) never set it: a notice with exactly one amount-shaped number and a missing or odd name has `amountGuessed: false`, keeps its name reason codes in `reasons`, is never `oneTap` / auto-confirmed, and is assigned with a plain assign (no `force`, no `amount`) when the amount equals the target's balance (otherwise the normal `amount_mismatch` rule). `amount_adjacent_to_name` is now evaluated for every name candidate even when a name reason is present (the amount is glued to sender-typed text -> `amountGuessed: true`). Rows stored before 3e keep their old `amountGuessed` value (conservative: it can only be stricter). **Glued amounts:** besides a name next to the number, `amount_adjacent_to_name` (amount uncertain) is also set when the number touches any non-space character before it (except the word `입금`) or a character after it other than whitespace / `. , : ; ) ]`, and when the number STARTS its own line with no `입금` label before it on that line (the layout where sender-typed digits would be glued to the amount). Bank templates print `입금 <amount>` on one line, so clean notices stay strict. Limit: sender text of digits placed directly after an `입금 ` label on the same line is indistinguishable from the real amount — **the SMS forwarder must be restricted to the bank's sender number**, otherwise anyone can send a text in a bank's shape. A deposit text with no amount at all is `unparsed`. The raw text (max 300 chars) is kept for staff.

**`byMethod`**: per payment method, `received` = sum of the payments recorded with that method (every payment is ledgered with its own method: cash 3,000 then transfer 5,000 gives cash 3,000 / transfer 5,000), `refunded` = refunds already handed back with that method, `net = received - refunded`, `count` = number of payments. **Σ `net` over the three methods = `totals.revenue`** and Σ `received` = `totals.paidAmount`. Orders from Release 1 are backfilled (hand-confirmed = `other`, automatic = `transfer`); the same object is in every day report and the CSV (section 결제수단별).
**Exact semantics (Release 2 — these changed):**
- `revenue` = **money actually received minus refunds already handed back** = `paidAmount - refundsDone`. `paidAmount` = sum of `paidAmount` over ALL orders (cancelled ones included: their money was received until it is refunded). It never counts unpaid balances.
- `refundDue` = open refund entries (money owed back, not yet handed back). While a refund is open the money still counts in `revenue`; marking it done (`refunds/<id>/done`) moves it into `refundsDone` and lowers `revenue`.
- `writtenOff` (미수금) = balances of unpaid, non-cancelled orders whose table was force-cleared; **never part of `revenue`**; an order leaves this list when it is paid later (its money then counts in `revenue`) or when the clear is undone.
- `billed` = sum of `total` of non-cancelled orders (what was charged, after discounts), the old "revenue" meaning. `unpaidRevenue` = balances of non-cancelled, unpaid, not written-off orders (still open at tables). `paidRevenue` = money received on non-cancelled orders. `orders`, `discount`, `memberDiscount`, `memberOrders` count non-cancelled orders as before.
- **Feature I:** cover orders are ordinary orders in every total (`orders`, `billed`, `paidAmount`, …); `byKind` splits them, `byItem` lists food items only, and `byMethod` counts every payment (a voided payment is not counted). `visitors`: per SEATING (table seat) by its `seatedAt` hour; `total` = Σ people, `parties` = seatings with a headcount, `partiesUnknown` = seatings with orders but no headcount, `avgPartySize` rounded to 0.1. Frozen in every day report; CSV sections 종류별 and 방문객.
- `byHour[].billed` / `.revenue` follow the same split, by the hour the order was created; `byItem` ignores cancelled orders; `qty` excludes service lines (`serviceQty`), `gross` is before discounts and excludes service lines.
Covers every seat since the last reset / day close. `label` is KST.

### Boot self-heal (rollback safety)
Older code (a roll-back to Release 1 and forward again, or a crash mid-migration) writes only the `paid` flag. On every boot the server trusts the flag wherever it contradicts the money recorded, then repairs the payment ledger. **Release 3b: the heal never CREATES money for an order that has payment-ledger rows (voided rows count): there the ledger wins and only the `paid` flag is repaired** (a: flagged paid with too little held -> flag cleared; c: cancelled / waived with nothing held -> flag cleared). Orders without any ledger row (true Release 1 data) keep the rules: (a) paid but money held < total -> `paidAmount` is raised to cover the total (method `other`); (b) unpaid but money held >= total -> `paidAmount` is reset to what was refunded, so the full balance is due again; (c) cancelled while paid and nothing recorded -> `paidAmount` = total and a refund entry (`legacy_cancelled`, dated with the cancellation) is created. Idempotent; one audit row `migrated` (`1차 버전 데이터 보정 · 주문 N건 ...`) is written only when something changed.

### Headcount, cover charge (입장료), share payments (각자 내기) — feature I
**Headcount (I1).** Each table SEAT has `people` (integer 1..30, `null` = unknown) and `seatedAt`. Clearing a table starts a new seat with `people = null`; undo-clear restores the old seat with its headcount; **table move**: the destination takes the source's `people` when it has none, otherwise the destination's `people` becomes the SUM (an unknown side counts as 0; both unknown stays unknown) and its cover order is re-priced to the merged headcount; the source starts a new seat. `reset` / day close delete all headcounts (the day report keeps `visitors`).
- Guest: `POST /api/t/<token>/party` body `{ "people": 1..30, "seat": <party.seat from the snapshot> }` -> `{ party }`. **`seat` is required** and bound to the seating the page was rendered for: 400 `bad_seat` when missing, **409 `seat_changed` `{ seat }`** when staff cleared the table meanwhile (a stale page of the previous party can never set people on the new seating — reload). Allowed only while `people` is `null` for the current seat and the guest may answer: 409 `party_set` afterwards (staff change it), 403 `party_not_asked` when `askGuest` is off AND the requirement is off, 400 `bad_people`. **Guests can always answer while `requireBeforeOrder` is on** (cover enabled), whatever `askGuest` says, so nobody is stuck without staff. Snapshot: `party: { seat, people, askGuest, required, canSet, updatedAt, seatedAt, setBy: "guest"|"staff"|"waitlist"|null, setAt }` (`canSet = people == null && (askGuest || required)`).
- Staff: `POST /api/staff/tables/<n>/party` body `{ "people": 1..30, "expectedUpdatedAt"? }` (any time; `expectedUpdatedAt` = `tables[].partyUpdatedAt`, 0 when nothing is set yet) -> `{ ok, party, coverOrder: Order | null }`. **`"dryRun": true`** -> `{ dryRun: true, party, coverOrder }`: the cover order as it WOULD become (total, `balanceDue` / `refundDue` / `overpaid`, `shares`), nothing written (no audit row, no state change). 400 `bad_people` / `bad_expected`, 404 `no_table`, 409 `stale` `{ party }`. A staff change takes over `setBy: "staff"`; the waitlist `seat` call sets `setBy: "waitlist"`. Audit `party_set`: `1번 테이블 인원 변경 3명 → 5명`.
- Waitlist `seat` with `table`: see Waitlist.

**Cover charge settings (I2).** `POST /api/staff/cover/settings` body any of `{ "enabled": boolean (default false), "mode": "per_person"|"per_table", "amount": won (multiple of 100, 0..100,000, default 0), "requireBeforeOrder": boolean, "askGuest": boolean (default true), "label": 1..12 chars (default "입장료") }` -> `{ ok, cover }` (the complete settings; also `state.cover`). Codes: 400 `nothing_to_update`, `bad_enabled`, `bad_mode`, `bad_amount`, `bad_label`, `bad_require_before_order`, `bad_ask_guest`. Audited with before -> after. `askGuest` is the switch for the guest headcount question and is independent of `enabled`.
**The cover order.** When `enabled` (and `amount` > 0) a seat gets exactly ONE cover order (UNIQUE key `cover-<table>-<seat>`): **per_person** — created when the seat's `people` is set (staff, guest or waitlist seat), one line `{ id: "cover", name: <label>, unitPrice: <amount>, qty: people }`; **per_table** — created with the seat's first order (or a headcount), one line qty 1. `kind: "cover"`, `createdBy: "system"`, status `served` from the start (never in the kitchen), `memberDiscount`/`couponDiscount` 0, no stock. It is NOT counted in the per-seat order caps (guests 40 / staff 80) or in `tables[].orderCount`; it is counted in `occupied`, unpaid totals, clear/unsettled checks, write-offs, sales (`byKind.cover`), day close and `reset` like any order.
- **Re-pricing:** changing `people` re-prices a per-person cover order with the unit price it was CREATED with (a later settings change only affects NEW seats; disabling the cover later changes nothing: existing orders keep following the headcount, no new ones appear). H2 rules: fully paid and unchanged -> nothing; lower after payment -> `paid: true` with `overpaid`/`refundDue` and an open refund entry (`edit_lower_total`); higher -> `paid: false` with a `balanceDue` and the refund entry disappears.
- **Untouchable by the normal endpoints:** guest cancel -> 409 `not_cancellable`; guest depositor, staff `status`, `items`, `service` and `move` -> 409 `cover_order`. A cover order cannot be moved alone; table merge: both seats with a LIVE cover order -> 409 `cover_conflict` (waive one first), otherwise the cover order moves with the orders and is re-priced to the merged headcount.
- **`requireBeforeOrder`:** when true (and cover enabled) a GUEST order is refused with 409 `party_required` until the seat has a headcount. It never requires payment: the cover can stay unpaid. Staff orders are not gated.
- **Waive:** `POST /api/staff/tables/<n>/cover/waive` body `{ "reason": 1..30 chars, "expectedUpdatedAt"? }` -> `{ ok, order }`: the cover order becomes `cancelled` (`note: "면제: <reason>"`, `waived: true`); money already received becomes a refund entry. 409 `no_cover`, 400 `bad_reason`. A waived cover is not re-created or re-priced. `POST /api/staff/tables/<n>/cover/restore` body `{ "expectedUpdatedAt"? }` -> `{ ok, order }`: back to `served`, re-priced to the current headcount, paid state and refund entries recomputed; 409 `no_cover` when nothing is waived. `tables[].cover` tells the UI (`{ orderId, status, waived }`). **3e — guest snapshot of a WAIVED cover:** `cover` = `{ enabled: true, waived: true, total: 0, left: 0, paid: <money still held>, ... }` even when the cover setting was switched off afterwards (`settingEnabled` still shows the setting): the page shows "입장료 면제". `enabled` is now `settingEnabled || a cover order exists on the seat (live or waived)`; seats without any cover order are unchanged.

**Share payments (I3).**
- A payment may carry `shares` (integer >= 1, ONLY on per-person cover orders: `amount` = `shares x unitPrice`) and `payer` (cleaned like a depositor: 1..10 visible characters, optional). `POST /api/staff/orders/<id>/paid` body `{ "paid": true, "method", "shares": 2, "payer"?: "김철수" }` derives the amount; `{ "shares": 2, "amount": 6000 }` is accepted only when equal; `{ "amount": 1000 }` stays a plain money payment (no shares). 400 `bad_shares` (not per-person cover, not an integer >= 1, or amount mismatch), 400 `bad_payer`. A shares payment with `paid: true` already fully paid is an explicit payment (not the double-tap `stale`). **`shares` can never exceed what is left:** more -> 400 `too_many_shares` `{ left }` (also stops a double tap from two phones). **3e: a share payment can never exceed the BALANCE either:** `shares x unitPrice > balanceDue` (e.g. 500 won still owed, unit 3,000) -> 400 `exceeds_balance` `{ balance, unitPrice, left }`, nothing is booked; use `payBalance: true` to take exactly the balance, or the explicit `{ amount }` form to take more deliberately (the excess becomes a refund entry); over-payment in money (`amount`) and refunds work as always (the money excess is a refund entry). `dryRun` previews it. Audit: `주문 #12 입금 확인 · 현금 6,000원 · 2명분 · 김철수 · 잔액 3,000원`.
- `shares: { total: people, paid, left, over }` — **Release 3b: counted from the MONEY held** (`held` = `paidAmount` minus refunds already handed back): `paid = min(total, floor(held / unitPrice))` (plain money payments count too; **`shares.paid <= shares.total` always**), `left = total - paid`, `over` = share-row shares beyond the headcount after it was lowered, limited to what the money still pays for (the money excess is a refund entry). So after lower -> refund done -> raise, or waive -> refund done -> restore, `left` is the number of shares really still due and payments `shares` up to `left` are accepted. Invariant: `left x unitPrice = balanceDue` while `held` is a multiple of `unitPrice`, and `balanceDue > 0` implies `left > 0`; `payments` as above. Guests of THAT table see `[ { shares, payer, at } ]` (their own party, the name as typed); other tables, the board and wait payloads never see names or headcounts.
- **Void a payment:** `POST /api/staff/payments/<id>/void` body `{ "reason": 1..30 chars, "expectedUpdatedAt"? }` -> `{ ok, order }`. Meaning: the entry was a MISTAKE and the money was never received (money really handed back is a refund). Effect: the payment row is kept but marked void (`voidedAt`, reason) and leaves `payments`/`shares.paid`; `paidAmount`, `totals.paidAmount`, `totals.revenue`, `byMethod.<method>.received` and `.count` drop by its amount (no refund entry); `paid`/`balanceDue`/`paidAt` are recomputed, open refund entries shrink with the money held; a deposit notice linked to that payment goes back to `pending`, a share intent paid by it becomes void. 404 `no_payment`, 409 `payment_void` (already voided), 409 `cannot_void` (refunds already handed back exceed what would remain), 400 `bad_reason`, 409 `stale`. Works on any order including cancelled ones and old seats. **3b:** if the void leaves an unpaid order on a seat that was cleared, the order is written off (미수금) like a force clear would.
- **Guest intents (no money moves; they only help staff match transfers):** `POST /api/t/<token>/cover/intents` body `{ "payer": 1..10 chars, "shares": integer >= 1 }` -> 201 `{ id, amount, shares, payer, expiresAt }`. Needs the existing `booth_d` device cookie (400 `no_device`), a live per-person cover order (409 `no_cover`), at most `shares.left` shares open in intents at once (409 `too_many_shares` `{ left }`) and at most 10 open intents per seat (429 `too_many_intents`); 400 `bad_payer` / `bad_shares`. **3b:** when the headcount drops, open intents that no longer fit (shares above the shares left, or amount above the balance) are cancelled. Intents expire after 30 minutes (no longer listed, no longer matched, no longer block shares). **Bounds:** at most 6 creates per device per minute and 30 rows per seat INCLUDING cancelled / expired / void ones (both 429 `too_many_intents`); cancelled / expired / void rows are deleted an hour after creation (on the next create and by the 30 s sweep), paid ones stay with their payment until the day is wiped. `POST /api/t/<token>/cover/intents/<id>/cancel` cancels the caller's OWN intent (device-bound; 404 `no_intent`). Staff: `state.coverIntents`, `POST /api/staff/cover/intents/<id>/cancel`. **Staff taking a share by hand** (`POST /api/staff/orders/<cover id>/paid` with a `payer`) with `shares` (or an amount that is a whole number of shares) closes the open intents of that seat whose payer equals it after normalisation (status `paid`, linked to that payment): the one with exactly those shares, else oldest-first while the shares cover them; any other amount closes none. A later transfer of theirs is then not booked as another share. (Quick share buttons without a payer close nothing.)
- **Deposit notices and intents:** besides whole-balance matches, a notice whose amount equals an OPEN intent's amount (same seat rules) is a candidate carrying `intent` — **only while it still fits** (`intent.shares <=` the shares left and its amount `<=` the balance). `recommended: true` marks a candidate only when ALL hold (Release 3b): the notice is strictly parsed (`amountGuessed` false and no parse reason code, see assign), it is the ONE candidate of any kind (orders and intents together) whose name equals the notice name, and every other same-amount candidate is on the SAME table OR carries a notice-shaped name (a nameless or placeholder-named candidate at another table: nothing is recommended and the notice gets `several_candidates`). Each notice carries `oneTap: boolean` — true exactly when one of its candidates is `recommended` (which also requires an empty `oneTapBlockedBy`: a hand-paid same-amount order or a repeated text blocks it, see Notice); the UI must offer one-tap confirmation only when `oneTap` is true; if an order and an intent both match name and amount none is recommended and the notice gets `several_candidates`. Assign with `intentId` (see Deposit notices). Auto-confirm (still OFF by default) fires for an intent when it is the ONLY candidate or the one picked by the `recommended` name rule above, the names are equal after normalisation and every other existing rule holds; otherwise the usual reasons (`several_candidates`, `name_mismatch`, …). A cover order's whole-balance candidate has no depositor name, so it is never automatic.
- **Guest snapshot `cover`:** `{ enabled, settingEnabled, label, mode, unitPrice, requireBeforeOrder, people, total, paid, left, waived, shares: { total, paid, left } | null, myIntents: [ { id, table, payer, shares, amount, createdAt, expiresAt } ], payments: [ { shares, payer, at } ] }` — `total`/`paid`/`left` are money (`paid` = held, `left` = balance); the Toss amount for a share is `shares x unitPrice`. **Release 3b: `enabled` is true whenever the setting is on OR the seat has a live (non-cancelled) cover order**, so switching the setting off never hides a charge that is still owed; `settingEnabled` is the raw setting ("will new seats get a cover"). Staff `tables[].cover` was always independent of the setting.

**Worked example** (cover `per_person`, 3,000 won): (1) 4 people sit down: guest `POST .../party {people:4}` -> cover order total 12,000, `shares {total:4,paid:0,left:4}`. (2) A taps "1명분 낼게요": `POST .../cover/intents {payer:"에이",shares:1}` -> `{id, amount:3000}`; A transfers 3,000, the bank SMS arrives: the notice lists the intent candidate (`recommended: true`); staff `POST /api/staff/deposits/<n>/assign {orderId:<cover order>, intentId}` -> paid 3,000, `shares {4,1,3}`, payment `{shares:1, payer:"에이", method:"transfer"}`, intent closed. (3) B pays 2 shares in cash: `POST /api/staff/orders/<id>/paid {paid:true, method:"cash", shares:2, payer:"비"}` -> paid 9,000, `shares {4,3,1}`, balance 3,000. (4) A fifth person joins: staff `POST .../party {people:5}` -> total 15,000, `shares {5,3,2}`, balance 6,000. (5) C pays the last 2 by transfer: `{paid:true, method:"transfer", shares:2}` -> `paid: true`, 15,000, `shares {5,5,0}`. (6) One person leaves after paying: `party {people:4}` -> total 12,000, `overpaid 3,000`, `refundDue 3,000` and an open refund entry (`edit_lower_total`); staff hand it back: `POST /api/staff/refunds/<id>/done {amount:3000, method:"cash"}`. Books: transfer received 9,000 (2 payments), cash received 6,000 minus 3,000 refunded, `byKind.cover` billed 12,000 / received 15,000, `visitors { total: 4, parties: 1 }`.

### Audit log (H13)
- `GET /api/staff/audit?before=<id>&limit=100` (both optional non-negative integers; anything else -> 400 `bad_query`) -> `{ entries: [ { id, at, action, target, summary, summaryKo, test } ], next: <id> | null }` (`test: true` = the row is about the test table; its `summaryKo` starts with `[테스트] `) — **`summaryKo`** is a Korean sentence staff can read as is (e.g. `주문 #12 입금 확인 · 현금 5,000원 · 잔액 3,000원`, `3번 테이블 강제 정리 · 미수금 1건 8,000원`, `메뉴 품절 표시`), present on every row (rows written before this field fall back to `summary`); `summary` / `target` stay the machine-readable English text. Never any secret in either, newest first (`limit` 1..200, default 100; pass `next` as `before` for the next page; `null` = end). The newest **5000** rows are kept; `reset` / day close keep them. Recorded actions (`action`): `test_reset`, `test_settings`, `party_set`, `cover_settings`, `cover_create`, `cover_update`, `cover_waive`, `cover_restore`, `cover_intent_cancel`, `payment_void`, `order_create_staff`, `order_status` (accept / served / undo, `from→to`), `order_paid`, `order_unpaid`, `order_cancel`, `order_edit`, `order_service`, `order_move`, `table_clear`, `table_unclear`, `table_move`, `refund_done`, `coupon_manual`, `coupon_void`, `coupon_redeem`, `deposit_assign`, `deposit_attach`, `deposit_dismiss`, `deposit_auto`, `menu_create`, `menu_update` (price / name / hidden / stock), `pay_settings`, `member_discount`, `notice` (old → new text), `ordering` (`true→false`), `table_count` (`40→30`), `table_rotate`, `deposit_secret_rotate`, `deposit_auto_setting` (`autoConfirm false→true, max 30000→20000`), `wait_timeout` (`5→7 min`), `reset`, `day_close`, `login`, `lockout`, `migrated` (boot self-heal, see below), and `staff_action` for the other staff writes (target = the endpoint with ids as `#`, summary = the NAMES of the sent fields only: menu delete / reorder / categories / photo / sold-out, rewards, hourly reward, award-hour, waitlist switches, ...). A test walks every staff POST route in `server.js` and fails if a state-changing one writes no audit row. Money actions are written in the same transaction as the change. **Never stored: PINs, session / login keys, table tokens, the deposit-hook secret, the account number, SMS text** (pay settings only list which field names changed).

## 7. Realtime (SSE)

Endpoints (all `GET`, `text/event-stream`):

| Endpoint | Auth | Channel |
|---|---|---|
| `/api/t/<token>/events` | token | that table (+ this device's nick) |
| `/api/staff/events` | staff | staff |
| `/api/kitchen/events` | staff | kitchen |
| `/api/board/events` | none | board |
| `/api/wait/<id>/events?secret=` | secret | one waitlist entry |

Each connection starts with `retry: 3000`, then an immediate `state` event, then another `state` whenever the snapshot changes (changes are coalesced ~120 ms; identical snapshots are not re-sent). `: hb` comment every 20 s. Headers: `Cache-Control: no-cache, no-transform`, `X-Accel-Buffering: no`.

**`event: state`** — `data:` is the full JSON of the matching GET endpoint: guest = `GET /api/t/<token>`, staff = `GET /api/staff/state`, kitchen = `GET /api/kitchen`, board = `GET /api/board`, wait = `GET /api/wait/<id>`. Frontends can render purely from `state` events.

**Hint events** (small, immediate, optional; use for sounds/flash). The same data also arrives in the next `state`:

| Event | Channel | Data |
|---|---|---|
| `new_order` | staff | `{ id, table }` |
| `new_call` | staff | `{ id, table, type }` |
| `new_wait` | staff | `{ id }` |
| `new_deposit` | staff | `{ id, status }` — a bank deposit notice arrived and needs staff (`pending` or `unparsed`) |
| `deposit_matched` | staff | `{ id, status: "matched" }` — a notice was matched automatically and the order marked paid (the normal `state` follows) |
| `payment` | staff | `{ orderId, table, amount, method, auto: boolean, kind: "food"\|"cover", shares?, test }` — emitted for EVERY payment row recorded by any path: staff pay, share payments, deposit assign (one hint per row), automatic deposit confirmation (`auto: true`); never for a dry run or a refused / rolled-back call |
| `payment_void` | staff | `{ orderId, table, paymentId, amount, method, kind, test }` |
| `new_cooking` | kitchen | `{ id, table }` — an order just became `cooking` (also for staff-created orders with `accept`) |
| `order_status` | guest | `{ id, status }` |
| `cleared` | guest | `{ seat }` — staff cleared this table or moved it away; state already shows empty lists |

Use native `EventSource` (auto-reconnects with the `retry:` delay; cookies are sent). Pattern: open `EventSource`, on `error` also start a 5 s poll of the matching GET endpoint until `open` fires again. **Connection limits.** When a limit is exceeded the server **closes the oldest stream** (so `EventSource` silently reconnects after its `retry:` delay) instead of rejecting the new one: max 5 streams per device cookie, max **12 per guest table**, max **20** on `/api/board/events`, max **60** on wait streams. Guest + board + wait streams together are capped at **300** (503 `busy` beyond that); staff + kitchen streams have their own pool of 100 (oldest closed), so public traffic cannot take their slots. Cookie rules: a guest stream always has a device (the server mints `booth_d` on the first guest request); board/wait streams without a valid `booth_d` all share one bucket per channel type, so a cookie-less client can only hold 5 of them. **Slow readers:** state events are full snapshots, so a stream that cannot keep up simply receives the latest snapshot when it drains (intermediate states are skipped); a public stream with more than 64 KB of unsent data is dropped (it reconnects). Hint events may be skipped for a slow reader. Do not open more than one stream per page, and close it (`es.close()`) on page hide/unload.

## 8. Behaviour notes the frontends must respect

1. A cleared table's guests keep the same URL; after `cleared` the page should show an empty state ("새 손님을 환영해요") and reset local cart/nickname.
2. Guests identify only by cookie `booth_d`; if the user blocks cookies, nickname/plays/wait will not work. Show a hint on 4xx from `plays/start`.
3. Orders need staff acceptance: after 201 show "접수 대기"; staff moves it to `cooking`, then `served`. `paid` is independent (staff sets after confirming the transfer).
4. Item coupons (`type: "item"`) cannot be applied to orders (`coupon_not_discount`); the guest shows the 6-char code full screen for staff to redeem.
5. Sold-out/open-close/clear changes reach guests through the `state` event; cart lines for a sold-out item should be greyed out and the 409 `sold_out` response (`ids`) used to highlight them.
6. Display `message` strings from errors directly; they are Korean and end-user safe.
7. **Storage ceiling (new).** The database has a hard 256 MB size limit. When it is reached every write answers **503 `storage_full`** (reads keep working). Show the Korean `message`; staff must be told (they can export the CSV and reset). Not expected in normal use.
8. **Board caching (new).** `GET /api/board` (and the board `state`) may be up to 1.5 s old; any play result, nickname, award, stock change, clear, move or reset refreshes it immediately.
